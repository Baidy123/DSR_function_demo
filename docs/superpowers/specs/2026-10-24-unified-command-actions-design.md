# 个人战术统一参与小队规划

状态：设计提案，待用户审阅；尚未修改运行代码，尚未进行本方案的行为验收。

依据：用户要求协调器统一遍历个人训练实际装配的战术，并能够使用全部战术；短程突进、火力压制也必须进入同一流程，不随动作数量增加专门的协调器接口。用户随后询问对原框架的影响，本稿以复用既有职责、控制迁移范围为设计取舍。

相关约束：[敌人 AI](../../enemy-ai.md)、[项目结构](../../project-layout.md)、[地图战术搜索设计](2026-10-23-squad-tactical-search-design.md)、[远近协同及训练审计](2026-10-24-ranged-melee-cooperation-design.md#11-个人训练能力的接入审计2026-10-24)。以下接口、字段和迁移方式是本稿建议，不是用户已经确认的实现细节。

## 1. 目标与框架影响

所有成功装配且具有团队适配的动作，均通过同一入口提供当前可执行方案。协调器根据整个队伍的目标、空间和配合需求选择组合，再命令原动作执行。条件不满足的动作说明原因，条件恢复后重新参与；不能因为目录顺序靠后、当前岗位已有一个执行器或没有专用分支而永久失去机会。

这属于调度接口的中等规模改造，涉及装配入口、候选准备和现有动作适配，不是重建整套 AI。保留以下职责：

- 区域提供唯一推进时钟；Squad 持有唯一团队任务所有权。
- 普通、强配合及单人幸存者都持续受协调器指挥；0级及无绑定成员沿用个人 Utility。
- AI 持有动作实例；Context 传递数据与公共查询；规划器比较整队方案。
- 原导航、身体碰撞、近战、射击节奏、弹药、感知和地图真实观察负责最终执行条件。
- 保留场景节点、训练资源、动作资源路径、脚本 UID 及用户当前工作区修改。

主要风险在候选数量增长、多阶段动作交接和旧任务连续性。方案必须同时约束这三项，不能只把 `for action in actions` 加进协调器便宣布完成。

## 3. 方案比较

| 方案 | 收益 | 代价/限制 |
| --- | --- | --- |
| **统一动作提案协议，推荐** | 动作负责自身条件和步骤，协调器统一收集、联合选择；新增动作不改选择器 | 需要为现有动作补齐团队提案适配，并验证预算和交接 |
| 完全用资源表描述全部动作条件与过程 | 简单动作配置方便 | 掩体出口、有限压制等过程需要复杂解释器，容易把每个动作的专门分支换成另一套规则语言；本轮不建议 |
| 直接收集个人 Utility 候选并执行个人 tick | 表面改动较少 | 个人候选可能带对象引用、个人选点、预约或动作切换，不能直接满足团队任务所有权和同步约束；不采用直接包装 |

推荐方案复用个人动作中的无副作用几何、条件与时序算法。需要共享时提取小型辅助函数，不复制整套个人 FSM，也不直接恢复普通/强配合中的个人选优。

## 4. 统一数据流与接口

```text
个人训练 + 兵种/装备资格
          ↓ 原 Library 装配
AI 持有实际动作，冻结本场能力
          ↓
协调器提出当前规划问题、共享几何机会和配合需求
          ↓ Context 统一查询通道
AI 在给定预算内遍历本场已装配动作
          ↓ 每个动作返回有限方案/不可用原因/继续准备游标
协调器核对权限、路线和身份 → 规划器比较完整小队组合
          ↓ 原子提交
AI 按 action ID 找到原动作 → 原命令执行入口 → 身体/火控
          ↓ 实际进展、完成/受阻、下一阶段条件
协调器保留、续接或重排
```

### 4.1 动作协议

保留 `freeze_command_capability()`、`command_runtime_state()`、`begin_command()`、`execute_command()` 和原取消/复位入口。拟增加两种所有动作共用的操作：

```gdscript
# 以下是接口草案，不是已提交的运行代码。
func prepare_command_offers(query: Dictionary, cursor: Dictionary,
        deadline_usec: int) -> Dictionary:
    # 返回 offers、next_cursor、done、reason。
    # 只能准备方案；不得开始移动、开火、消耗冷却或占用岗位。
    return {"offers": [], "next_cursor": {}, "done": true,
        "reason": &"command_adapter_missing"}

func validate_command_offer(query: Dictionary, offer: Dictionary) -> Dictionary:
    # 提交前及接单前核对该动作的当前条件。
    # 返回 valid 和 reason；不得借校验改变执行状态。
    return {"valid": false, "reason": &"command_adapter_missing"}
```

动作可返回多个方案，例如同一战术的不同掩体出口或压制用途。基础实现明确报告未适配，不能返回成功空壳并把它记为已支持。继承通用实现是允许的，但专用战术仍须提供自己的实质效果及验收。

角色保留为团队用途，如接敌、搜索、支援、侧翼、避险；动作 ID 只是查找执行器的键。新增同类战术不得增加 `choose_melee_rush()`、`can_suppress()` 等协调器专用接口。真正新增一类团队用途时可扩展通用合同，但不以每个动作的名字建立用途。

### 4.2 查询通道与所有权

使用 Context 的统一请求信号和纯值请求/结果槽，将准备或校验请求交给 AI 的通用处理函数。AI 连接该信号，只有 AI 遍历自己的动作对象；协调器及 Context 不保存动作实例、Resource、Script 或 Callable 形式的执行器目录。

查询在原协调器预算内同步返回一批结果，超过预算保存纯值游标，下轮续接；不新增每帧自主选动作循环或异步规划线程。Context 只传递数据，不能选择获胜动作。结果必须匹配请求身份，旧结果槽在复位、离队和重装后清理。

查询内容包括：本场与规划身份、成员能力版本、合法目标/证据及来源、本人身体与弹药状态、当前任务、通用岗位机会、地图/路线版本、队友需求和本轮截止时间。冻结能力与参数使用本场快照；冷却、弹药、受压和实际视野仍读取当前事实。

传给某名成员的事实遵守原通信范围。隐藏玩家坐标、共享目击冒充本人目击、未批准的 hint 精确位置不能作为查询捷径。

### 4.3 方案合同

共同字段在 `squad_contract.gd` 定义并校验，避免每个动作自行拼装不兼容任务：

| 字段组 | 用途 |
| --- | --- |
| 身份 | action、offer ID、profile ID、规划/目标/证据/地图版本；执行时使用原完整任务身份 |
| 用途与效果 | 承担的角色、可支持的真实队友需求、观察区域、攻击/保护作用 |
| 当前步骤 | 位置、完整合法路线、准备点、阶段关注点、姿态/速度和已有通用机动参数 |
| 过程 | 有限阶段说明、当前步骤完成条件、后续意图、失效条件及期限 |
| 代价事实 | 行程时间、不可攻击时间、暴露时间、预计观察收益等有共同单位的量 |
| 延续 | 原方案的稳定延续标识、阶段/剩余时限；评估不能重新领取时限或弹数 |
| 动作数据 | 该动作需要的纯值执行载荷；协调器只检查合法类型/大小，不按 action ID 解释 |

跨边界不携带掩体节点或其他对象引用。必要的几何关联使用实例 ID 加地图版本，执行前再核对存在性与所属区域；ID 不能代替真实有效性检查。

评分归整队规划器。动作提供可核对的效果和成本，不能自行声明“必须选我”的任意总分，也不能借个人 Utility 权重接管团队选择。默认分工是偏好，紧急换弹/身体占用/受压等依然是合法约束。

### 4.4 通用遍历示意

```gdscript
# 伪代码：仅说明所有动作共用同一调用流程。
# dispatcher 属于 AI；snapshot 和返回结果均为纯值。
for action_id in work.round_robin_actions:
    if Time.get_ticks_usec() >= deadline_usec:
        return pending(work)
    var action = installed_actions[action_id]
    var batch = action.prepare_command_offers(
        query, work.cursors.get(action_id, {}), deadline_usec)
    record_progress_and_reasons(work, action_id, batch)
    retain_bounded_valid_offers(work, action_id, batch.offers)

# 先完成本轮公平收集，再由既有整队规划器比较组合。
# 提交前，获选动作走相同的 validate_command_offer()。
```

这不是每帧穷举所有动作乘所有站位。描述符先筛掉完全不适用的阶段，几何服务提供可复用机会，各动作按游标分批准备。即使本轮结果容量已满，也要给后面的动作检查和替换候选的机会，不能沿用“前六个填满即停止遍历”的截断方式。

## 5. 全部现有动作的迁移范围

当前两个兵种目录合并后包含以下12个不同动作 ID。默认行为也通过同一提案入口，避免可选战术与默认行为各走一套选择流程。

| 动作 ID | 团队方案和应保留的实际效果 |
| --- | --- |
| `patrol` | 原巡逻岗位与实际到达；等待/警戒不虚报访问 |
| `search` | 原区域调查、覆盖责任与分阶段朝向；按真实观察完成，保留普通异步及强档关键入口同步 |
| `engage` | 远程合法射位与持续火力，参与交叉/后侧射界组合 |
| `melee_engage` | 实际可攻击的接近点，目标小幅移动后能恢复接近和命中 |
| `reload` | 真正补弹、可中断与恢复，配合原避险及队友支援需求 |
| `cover` | 躲藏、探出、开火/撤回及适用的低墙姿态，保留压力与安全条件 |
| `covering_retreat` | 移动撤退与合法同期射击，速度和开火条件由动作自身方案声明 |
| `attack_position` | 利用原攻击区域几何选位、移动和保持射击；不能只复用普通圆环点再换标签 |
| `suppression` | 可见支援、近身压力以及本人真实消失点的有限射击方案；用途、弹数和期限明确 |
| `cooperate` | 原受训侧翼/协作机动，路线与速度进入全队比较；沿途朝向合法威胁 |
| `melee_cover` | 掩体接近、合法出口、必要的观察/低墙过程和后续近战接敌；不能仅继承基础躲藏 |
| `melee_rush` | 距离/路线/冷却允许的有限突进，保留实际加速、剩余时间及原近战命中流程 |

`exit_suppression` 已是兼容迁移 ID，继续由原 Library 转换为统一压制；不因此恢复已退出的出口封锁、左右出口扫射或新增重复动作。

### 5.1 短程突进

把 `contact_executor()` 中对距离、冷却、路径耗时和目击/观察到换弹窗口的判断迁入突进的通用提案/校验实现。速度、持续时间和预计行程由方案表达；协调器不再识别 `contact_motion` 字段来另选动作。

冷却和加速计时仍归原动作管理，评估不启动计时；同一进行中方案延续时不重复开始突进。冷却结束或可用性改变通过共同状态版本/复查时间触发评估，不再由协调器查询某一类特殊动作。

### 5.2 火力压制

把用途选择、有限波次和退出条件纳入同一提案协议。原 Fire 继续负责真实开火，不新增压制枪械控制器。

本人消失点方案必须携带原始目击的瞄准点和事件身份，只消费一次，候选生成不消费。证据期限、实际发射扣数、完整枪口射线、射程、友军安全及原停顿条件都必须保留。不能把共享报告直接升级为本人失视事件，也不能读取隐藏目标修正弹道。

支援方案要在整队组合中绑定实际受益任务及尚未满足的需求。仅有 `support` 标签不授予长点射；被支援者完成、换任务、死亡或不再需要掩护时，按原规则结束支援。共享信息本身不允许开火；按原权限验证合法支援目标和射击模式。

当前任务合同默认 `attack=personal_sight`。若获选的是合法有限记忆压制，需经共同合同、提交校验、动作接单及 Fire 原证据检查明确传递该权限，不能只改字符串放宽所有命令动作的射击条件。

### 5.3 多阶段战术

提案说明当前步骤和有限后续意图，例如“借掩体接近 → 到批准出口观察 → 条件允许后接敌”。动作执行批准的当前步骤；需要换目的地、路线或占位时，向协调器提出下一步，由原事务重新核对和提交。

同一路线内已批准的速度、姿态、朝向及有限动作阶段可由原执行器推进。准备中的未来步骤不独占整条通道，也不因预计观察而写入覆盖记录。身体占用结束后仍由协调器核对续接；不能直接让个人 FSM 私自选新出口或恢复旧目标。

动作之间不获取彼此实例。近战掩体过程可复用近战接近的公共算法；若后续采用独立短程突进动作，由协调器从共同候选中另行分配，不能调用另一可选动作实例。

## 6. 联合选择、预算与连续性

1. 先核对实际装配、角色/装备资格、证据权限和几何，再比较完整队伍组合。纯远程继续评价交叉火力，混编继续评价近战接近路线与后侧射位，不设置固定兵种比例。
2. 每名成员的有限候选集合按职责/效果保留代表方案，再按共同成本淘汰；同一动作也不能用许多相似站位挤掉其他有效用途。仍保留当前有效任务和合法暂时警戒方案。
3. 遍历游标覆盖动作及其内部几何工作，按稳定轮询推进。某个动作暂无方案、准备中或校验失败要可诊断；不能把没有轮到视作不适用。
4. 复用协调器现有每次准备约2.5毫秒的预算与原几何查询批次。动作入口须拆分昂贵查询并遵守同一截止时间；不额外给每个动作一份完整预算。
5. 查询缓存键包含成员能力、目标/证据、地图及执行状态版本；同轮共享基础几何，动态枪线、弹药和身体条件提交前再核对。
6. 目标持续小幅移动时保留仍可复用的准备进度，在提交前验证最新合法目标。真正失效的路线或能力才撤销相关工作，保留此前修复的连续追击行为。
7. 重评不重置突进冷却、压制波次、观察计时和同一任务等待期限。共同状态用可用性版本、复查时间、活动方案身份及失败原因表达，具体动作状态由其自身解释。
8. 同一批次全员完成后沿用原完整组合规划和原子提交；旧方案失效时安排合法临时任务，不恢复个人 Utility。

候选容量和轮询步长在实测后确定，不能通过扩大预算或降低原门槛掩盖开销。本稿不承诺接口统一之后自然更快。

## 7. 文件与迁移边界

| 文件/模块 | 拟修改职责 |
| --- | --- |
| `actions/enemy_action.gd` | 增加统一准备/校验协议，保留共同命令执行与个人生命周期 |
| `enemy_ai.gd` | 遍历冻结装配的实际动作、处理统一查询及纯值结果；保持唯一执行动作 |
| `services/enemy_context.gd` | 统一查询通道、身份及结果隔离；不保存动作目录 |
| `services/squad_contract.gd` | 共同提案/阶段/效果字段和资格索引；取消“第一个动作就是唯一执行器”的调度语义 |
| `services/squad_coordination.gd` | 调用统一候选准备，保留目标、预算、完整任务表、事务和异常重排 |
| `services/enemy_team_planner.gd` | 比较动作提案的完整队伍组合，延用角色互补、空间和任务关联约束 |
| `services/enemy_search_formation.gd`、`squad_combat_tactics.gd` | 提供公共岗位、路线和联合几何成本；退出专门的动作选择 |
| `services/squad_defense.gd`、`squad_support.gd` | 保留压力事实/需求、真实支援关系及恢复逻辑；退出按动作 ID 选执行器 |
| `services/squad_search.gd` | 继续持有搜索/覆盖进度；使用明确的能力查询，不依靠第一个动作替代全部候选 |
| 各现有动作实现 | 把自身条件、纯值方案和命令执行接入共同协议；保留个人分支 |

不预先增加第二套行为树、全局技能管理器或通用规则语言。现有文件若因查询协议明显变大，可将 AI 内的遍历实现拆成一个私有辅助类；它仍归 AI 所有，不成为新的决策者。

建议分三个可验收阶段，正式实施计划在设计确认后细化：

1. 建立共同协议及预算遍历，迁移默认行为与现有突进/支援，保持真实追击和点射结果；增加无动作专用分支的扩展证明。
2. 补齐全部可选战术的实际过程，重点是攻击占位、近战掩体、有限压制及掩护撤退；移除被替代的专门选择通道。
3. 核对纯远程/混编的搜索与交战组合、连续性及性能，维护使用与测试文档。

阶段1允许在提交记录中明确尚未迁移的动作，不能称“所有战术已接入”。最终完成条件是目录全覆盖和下节行为验收，而不是协议文件存在。

## 8. 验收设计

| 验证 | 必须证明的事实 |
| --- | --- |
| 新动作扩展 | 测试新增一个 ID 不在生产选择器中的动作，只增加动作实现/定义/训练选择，即可被自动遍历、获选、实际执行并完成；不修改协调器分支 |
| 多动作竞争与顺序 | 同角色多个动作都获得准备机会；调换目录顺序不使有效战术消失；容量耗尽不饿死后续动作 |
| 全目录核对 | 动态枚举两个兵种目录及 includes；每个装配动作都有明确支持状态，12个现有 ID 均有实际效果证据或条件不满足对照；兼容别名不重复计数 |
| 训练和冻结 | 启用/禁用战术对照、参数变化影响实际行为、战中修改待重载生效；小队等级不授予未训练动作 |
| 突进 | 普通/强档、远处接近后进入窗口、冷却及受阻恢复；真实加速、后续命中、持续移动不被重规划反复打断 |
| 压制 | 实际扣弹/射击波次、有限个人记忆点、近身需求、真实队友支援；过期、硬墙、弹尽、换弹、失去需求及同事件重复提交均正确退出/拒绝 |
| 占位和近战掩体 | 到达原合法攻击区域并射击；实际借掩体接近、选择可行出口、观察和后续命中；继承基础藏身不计作完成 |
| 原协作 | 纯远程交叉、混编后侧火力、窄侧减少检查者/另一侧掩护、转角前后朝向、合法移动瞄准、奔跑及强档关键步骤同步 |
| 生命周期和权限 | 单人幸存、减员、死亡/离队、占用、重载、过时提案/任务反馈、无隐藏信息、指挥期间个人 Utility 仍为零 |
| 无副作用与预算 | 多次准备/校验不改变位置、弹药、冷却和预约；遍历能跨帧公平续接；沿用整队 P99 <16毫秒、峰值 <50毫秒门槛 |

优先扩展现有 `squad_command_contract_test.gd`、`squad_mixed_cooperation_test.gd`、原模块化/压制/近战专项和保存地图运行入口。实战测试按适用场景证明动作确实执行，不能人为把它们同时塞进一个场景后要求每种动作强制轮流出现。

不改用户保存场景、训练/武器资源以迎合用例；独立实例可改变初始位置、装备和训练。记录基线、最终实测及未通过项，不放宽原断言或把动作标签当成开火/命中证据。
