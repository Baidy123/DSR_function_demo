# 小队节点与调度器结构草案

日期：2026-10-13。2026-10-14 用户要求按本方向优化 AI 代码与结构；具体落地与验证见[实施记录](../plans/2026-10-14-squad-node-coordinator.md)。以下方案比较和建议保留设计阶段含义，不将实现选择追写为用户逐项确认的要求。

## 先看这几条

- 一个小队对应一个 `Squad` 父节点，成员放在它下面；节点挂载的脚本承担小队调度。
- 选中小队节点即可设置团队意识等级和队级参数。成员的兵种、个人 Training、武器和行动能力继续独立。
- 小队决定谁包抄、谁等待、谁掩护，以及集中还是分散；个人负责判断自身能否执行、寻找路线、移动和实际射击。
- 区域保留导航、合法情报共享和跨队空间协调。同阵营、同通信组的两个小队可以共享情报，但各自安排任务。
- 这次优化解决职责归属和编辑配置入口；性能仍需实测，不能把增加小队节点等同于性能改善。

## 1. 用户方向与本轮范围

**用户已明确的要求：**

1. 同一小队的单位统一归到一个节点下面，节点脚本就是调度器，在节点上配置团队配合等级等队级内容。
2. 只共享团队意识这项战术配置；不同兵种仍有各自的个人 Training 和战术行为。
3. 保留三档：仅视野共享、自主战术配合、训练有素的强配合。强配合包含等待队友、按局势部署，以及进攻、撤退、换弹时的掩护与火力压制。
4. 调度器负责团队安排，个人负责实施。设计不能限定为敌人针对玩家，后续需支持其他阵营。
5. 先结束当前一轮测试，再考虑结构调整；本轮请求是将 brainstorming 写成文件。

**本草案提出、尚未逐项确认的设计：**采用下述区域／小队／个人三层边界；小队用 `Node3D`；明确小队身份、配置来源、更新入口和迁移兼容规则。具体脚本名、字段名及接口分组均为建议，不冒充用户指定。

本轮不增加新战术算法、不重做个人决策框架，也不展开完整的多阵营感知和伤害改造。后者需要独立验证，不能仅靠命名中性就宣称完成。

之前的[三档团队意识设计](2026-10-13-team-cooperation-levels-design.md)与[实施记录](../plans/2026-10-13-team-cooperation-levels.md)保留历史含义。其当时不新增节点的约束，不应被悄悄改写；本草案记录用户后来提出的结构方向，继续保留原有三档行为与权限约束。

## 3. 方案比较

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| **推荐：小队拥有调度，区域保留公共服务** | 节点、配置、成员和计划一一对应；队与队之间边界清楚 | 需要从现有共享服务中抽出队级状态，并调整 Context 的路由 |
| 只新增分组节点和配置入口 | 场景编辑调整较小，可作为过渡 | 计划仍集中在区域服务，后台职责和队伍身份问题没有完整解决 |
| 每个小队复制一整套现有共享服务 | 队内状态容易隔离 | 导航／情报缓存容易重复，跨队避让与射线安全需要重新协调 |

推荐方案保留现有区域基础设施和个人执行链，集中调整与小队归属直接相关的部分。

## 4. 场景树与编辑体验

以下名称仅为示意，实施时保留现有成员名称和成员内部节点路径：

```text
Arena                       区域环境与公共服务
├─ CombatZone
├─ NavigationRegion3D
├─ Squad_A                  Node3D + SquadController 脚本
│  ├─ RangedUnit             兵种、个人 Training、武器、AI
│  └─ MeleeUnit              兵种、个人 Training、武器、AI
└─ Squad_B                  Node3D + SquadController 脚本
   ├─ RangedUnit
   └─ RangedUnit
```

选中 `Squad_A`，可以直接编辑三档团队意识、对应队级参数，以及建议放在队上的阵营和通信组。成员检查器显示所属小队与生效等级，并提供跳转到小队配置的入口；个人 Training 中其他战术继续独立编辑。

小队节点兼作场景摆放容器，默认使用无偏移、无缩放的变换。运行中的集中、分散和包抄由成员正常移动实现，不通过移动父节点完成。未来迁移必须保留成员世界位置、场景保存归属、资源引用和脚本 UID；引用成员外部路径的地方单独核对，成员内部 AI 路径保持原样。

建议文件落点沿用现有目录：`scenes/world/squad.tscn`、`scripts/world/squad_controller.gd`。可将抽出的队级状态与协议实现在 `scripts/enemy/services/squad_coordination.gd`，由节点独占一个实例。节点负责成员、配置和调度入口，内部服务负责计划状态及事务；区域不得再保留同一份计划的副本。暂不为统一命名而迁移整个 `enemy` 目录。

## 5. 三层职责与依赖

| 层级 | 拥有的数据和职责 | 对其他层的边界 |
| --- | --- | --- |
| 区域 | 导航、战术地图、激活时钟、阵营关系、合法共享观察、所有成员的位置和公共空间预约 | 提供环境与资源约束，不替显式小队选择岗位或推进包抄阶段 |
| 小队节点及其内部服务 | 成员集合、共享团队意识、成员上报、战术建议、岗位、部署、等待阶段、支援关系、交接、期限和失败记录 | 只安排本队；读取公共服务与个人提供的候选，不直接操纵身体 |
| 个人单位 | 个人 Training、能力、感知、自身记忆、Utility 选择、路线、身体、弹药和实际开火反馈 | 根据能力与安全条件执行或拒绝，并上报原因；不替整队改写计划 |
| 纯 planner | 对指定小队的值快照生成有界候选方案 | 不读场景树，不查询导航或射线，不保存跨调用运行状态 |

共享观察与任务占用要按含义拆分。例如“某位置已检查”的观察事实可按原有权限共享；“本队安排谁检查”“本轮已完成哪些步骤”属于小队。不能按字段名前缀机械搬运。

所有层都保留原有情报权限：调度器不能读取目标的隐藏真实位置，也不能绕过观察时效或通信限制。个人局部移动仍使用区域级成员位置和空间预约，保证不同小队的友军之间也能避让、避免挡枪。

## 6. 小队身份、成员和配置

**小队身份独立于阵营、通信组和配置资源。** 区域登记每个显式小队时分配独立运行身份，可沿用协议中的 `team_id` 概念；节点名称、路径以及 Resource 引用都不作为小队合并依据。两个队引用同一个训练模板，也只共享配置值，不共享计划或运行状态。

建议成员归属规则：在所属区域边界内，单位属于最近的 `Squad` 祖先。允许普通收纳节点夹在中间；遇到内层 `Squad` 后，外层不再领取其成员。嵌套只表示场景组织，不引入上下级指挥功能。每个单位在同一时刻只能登记到一个小队。

建议配置来源如下：

| 内容 | 显式小队中的来源 | 保留的兼容行为 |
| --- | --- | --- |
| 团队意识等级及参数 | 小队持有的 `cooperation_settings.gd` 配置资源 | 旧资源格式和 UID 保留；节点上的等级入口编辑同一资源，不另存一份等级 |
| 有效阵营与通信组 | 建议由小队节点统一提供，队内成员继承生效值 | 保留单位原有序列化字段，脱离显式小队后按旧配置处理，不自动回写个人资源 |
| 兵种、个人 Training、武器和能力 | 每个单位自身 | 不复制、不统一，不把整个 Training 提升为队级配置 |

新建小队建议默认“仅视野共享”，并使用独立配置实例；这是本草案的默认值建议。迁移已有小队时保留它当前生效的等级和参数。若用户主动让多个小队引用同一个外部资源，应明确提示编辑该模板会影响这些小队的配置，但运行状态始终独立。

成员关系、阵营关系和通信权限分别判断：同阵营可以影响友军安全判定，同通信权限可以允许情报交换，只有同一个小队的有效成员才能接到该队的岗位和支援承诺。跨队联合指挥不在本次范围。

## 7. 三档行为保持什么

| 等级 | 小队可以安排什么 | 个人如何实施 |
| --- | --- | --- |
| 第一档：仅视野共享 | 提供合法共享情报，不下发团队战术岗位 | 独立决策；基础避让、友军枪线安全继续生效 |
| 第二档：自主战术配合 | 根据局势和队友站位提出包抄、互补射位等建议 | 在正常 Utility 中比较建议与个人行为，可以接受或拒绝；没有强制同步等待 |
| 第三档：强配合 | 安排集中／分散／保持位置、必要参与者就绪等待，以及进攻、撤退、换弹的支援和火力交接 | 接受后遵守岗位与阶段协议，同时校验自身能力、路径、弹药和安全条件；失败立即反馈 |

强配合也不能要求近战单位完成远程压制，或把“已分配支援角色”当成“已经形成火力”。支援成立依赖真实执行反馈，等待与交接保留期限、退出和降级规则。无可用队友时回到可执行的个人行为，避免单人空等或主动补弹候选长期堵住其他行动。

本次先保持现有战术结果和能力限制，调整调度归属；不借结构迁移提高团队指令权重或降低现有验收要求。

## 8. 数据流、接口与更新入口

一次正常协作沿现有选择和事务协议进行：

1. 个人感知向区域发布允许共享的观察；个人将能力、候选、个人行为基线和执行事实提交给所属小队。
2. 小队收集本队有效成员及可见情报，形成值快照，调用现有纯 planner。
3. 第二档发布建议；第三档发布岗位和阶段要求。个人仍通过正常候选选择进入执行。
4. 接受岗位时校验小队身份、成员代次、配置版本、计划版本及期限，并通过区域服务准备公共空间预约。
5. 个人几何／能力校验成功后，按现有准备、提交、回滚约定完成岗位与预约；任一步失败都释放临时占用，不能留下半提交的岗位或预约。
6. 个人上报到位、开火、受阻、换弹或结束等事实，小队推进阶段或修复计划；过期反馈不能恢复旧承诺，修复也不能无限延长期限。

Context 建议保留两个清楚的服务引用：`cooperation` 连接区域公共服务，新增 `squad_coordinator` 连接队级调度。原有个人动作通过 Context 查询，尽量保留外部调用形式；内部按职责转发，不让各动作自行遍历场景树。

| 接口分组（建议） | 归属与依赖 |
| --- | --- |
| 注册区域成员、注册小队、查询关系和合法观察 | 区域；不依赖具体小队规划算法 |
| 公共空间预约的准备／提交／回滚／释放 | 区域；记录所属小队及版本，支持定向失效 |
| 注册队员、提交候选与基线、读取建议或岗位 | 小队；使用本队成员数判断协作资格 |
| 接受建议、岗位事务、执行报告、阶段推进 | 小队；借助区域预约服务，保留现有反馈协议 |
| 服务发现、队伍变化处理、个人执行查询 | Context；分别管理区域连接与小队连接 |

新增小队节点不要实现用于识别区域的 `enemy_environment()`，否则当前 Context 的祖先查找会把小队误当作区域。区域预约也不反向读取小队内部计划字典；通过明确的所有者／版本和释放或失效通知完成清理。

建议由区域统一推进已注册小队：一个区域时钟、每个物理帧每队至多推进一次，队内沿用现有调度周期。小队不再同时运行另一条独立的完整调度循环，旧区域逻辑也不得重复规划显式小队。

规划预算保持现有边界：每次纯 planner 调用最多 36 次组合尝试、2048 次冲突检查，各战术共用预算；这是每次调用的限制，不是已有的全区域预算。区域战术地图仍每帧最多推进 4 点，个人候选仍遵守既有 24 点／2000 微秒额度，不按小队复制地图缓存或重置区域额度。多队总开销需要单独测量，不能凭调用上限断言性能合格。

## 9. 生命周期与异常处理

| 情况 | 预期处理 |
| --- | --- |
| 初次进树、晚加入或普通容器层级变化 | Context 重新确认区域与最近小队；注册幂等，尚未完成连接时只运行可用的个人行为 |
| 同一区域内换小队 | 释放旧队岗位、建议接受状态和相关预约；更新成员代次。保留健康、弹药、个人 Training、自身感知记忆和原有出生点 |
| 跨区域迁移 | 按现有环境解绑规则清理旧区域引用、导航和空间状态，在新区域重新验证；不能携带旧计划或旧共享情报的权限 |
| 死亡、离队、节点释放 | 从小队及区域有效名册中移除，撤销支援关系和占用；其余成员重评，过期报告按身份与代次丢弃 |
| 等级、参数、阵营或通信组变更 | 更新配置／关系版本，立即失效不再合法的队级安排与共享快照；身体按原协议安全退出受保护动作片段，不强行重置身体状态 |
| 小队缺少配置或配置无效 | 给出节点诊断，停用团队战术安排，保留合法情报与个人行为；不静默借用其他小队或旧区域的配置 |
| 队内只剩一人、全员空弹或无合适支援者 | 不发布不可兑现的等待或支援承诺；允许必要的个人换弹、自救和其他合法行为 |
| 区域复位 | 统一使旧计划／反馈代次失效，清理队级状态和区域预约，再按原流程复位单位；每个单位只复位一次 |

区域当前会遍历直属目标并补上登记的嵌套成员。迁移后不能同时让小队递归调用成员 `reset_target()`、又让区域逐个调用，造成双重复位。小队状态复位与单位身体复位分别由明确入口负责。

## 10. 旧场景兼容与迁移边界

显式小队成员优先使用所属节点的配置和调度，并从旧的“阵营＋通信组”自动组队路径中排除。同组的未迁移成员不能被旧逻辑重新并入显式小队。

未放入小队节点的旧单位仍按原区域绑定和个人配置兼容规则运行。兼容入口复用抽出的队级实现，以区域持有的旧模式实例承接；不保留第二套规划算法，也不自动向用户场景树添加隐形小队节点。该兼容实例只管理未迁移成员，其所有权与显式小队实例互斥。

现有绑定资源和脚本 UID 保留以便旧场景加载。迁移某个场景后，明确移除该场景已被替代的绑定条目，避免编辑器出现两个有效配置入口；尚有未迁移成员使用的绑定继续保留，并标明兼容用途。

实际迁移需先列出本次涉及的成员和外部引用，包括场景 NodePath、信号、动画路径、测试夹具、调试面板和复位入口。按用户当前本地场景操作，保留成员、世界位置、武器、Training、导航及其他已有修改，不通过远端场景替换本地工程。检查器同步支持小队配置跳转、保存重载和撤销重做；独立查看 Training 资源时不虚构所属小队。

## 11. 验收与性能边界

实施后的结构与运行行为都要验收：

- **归属与隔离：**同阵营、同通信组、甚至共用配置模板的两个小队，成员与计划仍独立；每份队级状态只有一个所有者，显式成员没有进入旧分组路径。
- **配置与编辑：**节点设置是唯一生效入口，成员个人 Training 保持独立；保存重载、撤销重做和共享模板编辑符合说明。
- **公共环境：**不同小队的合法情报共享、友军避让、枪线安全和空间预约仍有效；区域地图只维护一份，更新次数不因增加小队重复。
- **生命周期：**加入、离队、同区域换队、跨区域迁移、死亡、热切等级和区域复位均清理旧承诺；没有重复登记、过期报告复活计划或双重复位。
- **真实行为：**三档均走正常 AI 循环；混合兵种按实际能力接任务，等待、两面包抄、站位、进退与换弹支援继续有真实行动和开火证据。覆盖单人和无弹药等退化情况。
- **目标抽象：**队级协议用成员／目标身份，不写死玩家；用不同阵营和目标快照验证隔离。完整非玩家感知、选敌和伤害链仍需后续专项，不能用协议测试替代。
- **回归与性能：**运行受影响专项、完整敌人组和必要的战斗回归；用相同夹具、准确人数、独占运行环境比较迁移前后，保留原性能阈值和失败记录。

性能对照至少包含 1／2／3／6 人，并比较“一个六人队”“两个三人队”“三个两人队”。分别记录个人 P99／最大耗时、区域和各小队调度耗时、全部 AI 总耗时、规划次数及空间查询量，避免只看单个小队变快。

当前已知基线：上一轮支援专项 **32/32**、场景整合 **25/25**；完整敌人组首轮 **71/110**，之后是定向复核，不能称完整回归全绿。最新六人强配合样本全部 AI 总耗时 P99 **52.415 毫秒**，个人 P99 **17.202 毫秒**，仍高于原个人 P99 **16 毫秒**要求。原个人最大耗时 **50 毫秒**要求也保留；总耗时与个人阈值分开报告。详细轮次见[测试记录](../../enemy-tests.md)。

这些遗留问题不因文档或节点迁移自动解决；若后续需要算法优化，应另列变更和对照结果。本轮只新增设计文档，进行静态自查和引用核对，不重跑未改变的运行代码。
