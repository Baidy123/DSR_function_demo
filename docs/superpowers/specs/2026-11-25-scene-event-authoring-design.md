# SceneDirector 检查器事件编排总设计

日期：2026-11-25。

状态：待用户书面复核；本文只定义目标架构、编辑体验、迁移边界与验收要求，尚未授权实施。

## 1. 用户要求与已确认方向

### 1.1 用户明确要求

1. 当前事件脚本缺少统一归属和清晰结构，需要整合。
2. 所有与场景事件编排有关的能力应属于一个统一体系，再向下区分具体内容；范围不能只覆盖生成敌人、镜头调度和对话。
3. SceneDirector 可以继续作为协调所有事件脚本的场景导演。
4. 主要编辑入口使用 Godot 检查器中的可增删、可排序队列，不把每个事件步骤铺成场景树节点。
5. 跨对象、存在先后顺序、会改变剧情或关卡流程的行为归导演；单个对象自身的局部能力仍由对象负责。
6. 事件内部先保持线性动作队列；条件分支拆成多条带不同条件的事件，不在首版引入节点图或脚本语言。
7. NPC 的剧情固定移动必须纳入事件动作，包括移动到点、沿固定路线、转向、显隐、入座和离席。

### 1.2 成功标准

- 选中 SceneDirector 后，可在一个检查器入口找到本场全部流程事件。
- 每条事件清楚表达“何时触发、需要什么条件、依次做什么、失败怎么办”。
- 添加动作时先按类别选择，再只显示该动作需要的参数。
- 新增动作不再扩张一个包含所有字段的万能 Resource，也不要求在导演核心继续添加字符串分支。
- NPC、门、Wave、对话界面、任务和装备等业务组件仍是各自行为与数据的所有者。
- 现有酒馆、开场和五关可以分阶段迁移；未迁移内容继续工作，不破坏节点路径、资源引用、脚本 UID 和用户保存参数。

## 2. 当前实现与问题

当前运行基础已经具备：SceneDirector 统一请求身份、排队、前台占用、暂停、取消和切场事务；SceneEvent 适配原信号；SceneFlowRule 按触发和条件运行；SceneFlowAction 可等待、刷波、演出镜头、切场和运行脚本。

主要问题位于作者侧结构，而不是完全缺少调度能力：

| 当前方式 | 问题 |
| --- | --- |
| `SceneFlowAction.Kind` 大枚举 | 所有动作字段堆在同一个类中；每增加能力都要修改枚举、字段显示和 Runner 分支 |
| `request_action(&"script", parameters)` | 类型与参数依赖字符串约定，检查器无法表达动作真实职责 |
| `CALL_METHOD` / `RUN_SCRIPT` | 通用出口掩盖了“移动 NPC”“发装备”“开门”等具体语义 |
| `Opening`、NPC、交互效果及世界脚本各自发请求 | 运行上经过导演，但作者无法在一个地方看出完整流程 |
| SceneEvent、Wave Events、SceneRules 和交互 Effect 并存 | 各自合理，但触发、局部交互和跨对象事件的边界不够直观 |
| 场景树中的 `Opening/EquipmentGrant` 等提供者 | 能执行，却不属于统一的事件目录；路径和职责难以追踪 |

本设计不推翻现有调度核心，而是在其上建立统一、类型安全的检查器事件模型，并逐步让现有流程使用它。

## 3. 边界：什么归导演，什么不归导演

### 3.1 归 SceneDirector 事件编排

满足任一条件的行为应作为事件动作：

- 操作两个或更多场景对象；
- 需要等待上一步完成再继续；
- 会改变剧情、任务、关卡或场景生命周期；
- 需要与对话、商店、镜头、暂停、死亡或切场协调；
- 需要在取消后停止 Tween、Timer、路线、界面或其他持续过程；
- 需要作者在一个队列里阅读完整演出。

例如：镜头看向门口 → 显示 NPC → NPC 沿路线进场 → 对话 → 发装备 → NPC 离场；玩家进入区域 → 关闭门 → 生成增援 → 等待清场 → 更新任务 → 开放出口。

### 3.2 保留在业务组件

- NPC 的寻路、避障、步行动画、座位占用和实际姿态。
- Wave 的模板、Squad/Enemy 部署、出生空间、导航检查、生成提交和清场统计。
- 门、帘幕、屏障和机关的实际动画及碰撞切换。
- DialogueUI 的对白显示与 Dialogue Manager 资源解析。
- Equipment、GameState、QuestController、ShopController 的库存、金钱、任务和购买结算。
- 摄像机的实际插值、遮挡和 Phantom Camera 接入。
- 单个交互物内部的简单可复用反应，例如只翻转自身旗标或播放自身声音。
- NPC 日常循环巡逻、随机闲逛和不参与剧情顺序的环境行为。

导演只调用这些公开能力并等待结果，不复制它们的数据或算法。

## 4. 检查器数据结构

SceneDirector 新增唯一作者入口：

```text
SceneDirector
└─ Event Sequences: Array[SceneEventDefinition]
   ├─ Warehouse Reinforcement
   │  ├─ Identity
   │  ├─ Triggers
   │  ├─ Conditions
   │  ├─ Actions
   │  └─ Failure Policy
   └─ Open Exit After Clear
      └─ ...
```

不新增 `SceneDirector/Actions`、`Events` 或每步动作场景节点。Wave、路线、Marker3D、NPC、门和其他真实空间对象仍保留在场景树中，事件资源用 NodePath 引用它们。

### 4.1 `SceneEventDefinition`

每个数组元素代表一条完整事件，至少包含：

| 字段 | 含义 |
| --- | --- |
| `event_id` | 场景内稳定 ID，用于诊断、存档扩展和去重；不能依赖显示名称 |
| `label` | 检查器显示名称，例如“仓库增援” |
| `enabled` | 临时关闭该事件，不删除配置 |
| `scope` | `SCENE` 本场一次；`REGION` 每轮区域可重播 |
| `trigger_mode` | `ANY` 任一触发；`ALL` 全部触发 |
| `triggers` | `Array[SceneTrigger]` |
| `conditions` | `Array[SceneCondition]`，全部满足才开始 |
| `actions` | `Array[SceneAction]`，按顺序执行 |
| `failure_policy` | 默认停止并报告；必要时可选择跳过失败动作 |

首版不提供任意跳转、循环、标签或嵌套分支。需要分支时建立两个事件，共用触发但配置相反条件。需要重复行为时优先由目标组件提供循环能力，或使用 REGION 事件随区域复位。

### 4.2 触发器

触发器表达“什么事情发生了”，不执行行为。保留并类型化现有 SceneEvent/SceneEventTrigger 能力：

- 节点信号：区域进入、交互成功、Wave spawned/cleared、Timer timeout、NPC 路线完成等；
- 导演生命周期：场景准备完成、区域开始、区域复位、场景完成；
- 状态变化：旗标、任务、阶段、物品或金额变化；
- 手动触发：脚本使用稳定 `event_id` 通知导演；
- 对话提示：DialogueUI 将对白标签转换为明确事件，不让动作解析任意台词文本。

信号参数过滤继续支持精确值和节点组；无效路径、错误信号、参数索引或类型不匹配必须在编辑器/启动诊断中报告。

### 4.3 条件

条件表达“当前仍允许执行吗”，与已经发生的触发事实分开：

- 旗标为真/假；
- 拥有物品或数量达到下限；
- 任务或阶段处于指定状态；
- Wave 状态；
- 节点存在、可见、启用或属于指定组；
- 玩家存活、位于区域或当前可交互；
- 公共只读查询适配，用于尚未类型化的业务条件。

条件在事件准备开始时检查；若事件因对话或商店排队，真正开始前必须再次检查。条件失败表示继续等待或本轮不执行，不冒充动作失败。

## 5. 类型化动作体系

### 5.1 基类契约

所有动作继承 `SceneAction` Resource。Resource 只保存配置；每次执行由 Runner 建立独立运行实例或执行上下文，不能把进度写回共享资源。

概念接口如下，最终签名在实施计划确定：

- `validate(context) -> diagnostics`：开始前检查配置、路径和目标能力；
- `start(execution) -> result/pending`：启动动作；
- `cancel(execution, reason)`：真正停止本动作创建或请求的持续工作；
- 单一终态：completed、failed、cancelled；
- 可声明前台/后台、暂停需求、玩家控制需求和区域/场景作用域。

动作不能直接调用下一个动作。Runner 只在当前动作完成后推进队列；旧回调必须携带执行身份，不能推进新一轮事件。

### 5.2 动作分类与首批目录

分类用于检查器查找和文档组织，不改变调度优先级。

首批核心动作的分类总览如下。这里展示稳定的主干类型；后文列出的扩展动作继续归入对应类别，不需要回到单一大枚举中堆叠字段。

```text
SceneAction
├─ Flow
│  ├─ WaitAction
│  ├─ WaitSignalAction
│  └─ CompleteSceneAction
├─ Combat
│  ├─ SpawnWaveAction
│  └─ WaitWaveClearedAction
├─ Presentation
│  ├─ CameraAction
│  ├─ DialogueAction
│  └─ PlayAudioAction
├─ Actor
│  ├─ MoveActorAction
│  ├─ SeatActorAction
│  └─ SetActorVisibleAction
├─ World
│  ├─ SetDoorAction
│  └─ CallInteractionAction
├─ State
│  ├─ SetFlagAction
│  ├─ GiveEquipmentAction
│  └─ UpdateQuestAction
└─ Transition
   ├─ ChangeSceneAction
   └─ RestartSceneAction
```

#### 流程 `Flow`

- 等待时间；
- 等待信号/事件；
- 等待条件成立；
- 完成场景；
- 结束当前事件。

#### 角色与 NPC `Actor`

- 移动到 Marker3D/Node3D；
- 沿 TavernRoute 或其他兼容路线移动；
- 面向玩家、节点或世界位置；
- 显示、隐藏或到达终点后离场；
- 入座、离席；
- 播放角色表现动画；
- 必要时瞬移，仅用于初始化或不需要演出的切位。

#### 战斗与生成 `Combat`

- 请求指定 Wave 出场；
- 等待指定 Wave 出场成功；
- 等待 Wave 清场；
- 启用/关闭战斗区域或合法战斗许可；
- 生成/移除非 Wave 场景对象，如剧情道具或一次性效果实体。

敌人动作只能调用当前 Wave/Director 公开入口。它不能自行实例化 Enemy、跳过出生空间与导航检查、改写 Squad/Enemy 层级、直接命令敌人 AI，或把“请求成功”冒充“真实生成完成”。

#### 表现 `Presentation`

- 展示目标点；
- 播放 CinematicShot3D；
- 打开并等待对话；
- 播放角色/场景 AnimationPlayer 动画；
- 播放/停止音效和音乐；
- 生成视觉特效；
- 显示/隐藏教程、提示或指定 UI。

#### 世界与机关 `World`

- 打开、关闭或切换门、帘幕、屏障；
- 启用/禁用节点或碰撞；
- 启动可取消机关动作；
- 设置节点显隐；
- 调用明确注册的交互/世界动作提供者。

#### 状态、任务与奖励 `State`

- 设置/切换旗标；
- 写入受支持的状态值；
- 更新任务或阶段；
- 发放物品、武器、弹药和医疗包；
- 发放金钱或显式奖励；
- 打开并等待商店。

状态动作调用业务模块的公开事务接口。导演不保存库存、任务、金额或购买状态，也不猜测不可逆结算的回滚方式。

#### 场景流转 `Transition`

- 重开当前场景；
- 切换到指定场景；
- 返回酒馆；
- 加载存档；
- 显示死亡/完成结果并等待选择。

继续沿用现有 prepare/validate/commit/discard 场景切换事务，排队、拒绝或加载失败不能提前写入检查点、奖励或玩家快照。

#### 高级扩展 `Advanced`

- 运行实现统一可取消契约的自定义提供者；
- 调用公开方法作为迁移后备。

通用方法调用不能成为新增常规功能的默认做法。某类行为出现两次以上或需要专用参数、取消及诊断时，应升级为明确的动作子类。

## 6. NPC 固定移动设计

剧情固定移动属于 `Actor` 动作，不属于 NPC 日常 AI。

### 6.1 移动到点

动作引用 NPC 和目标 Marker3D/Node3D，可配置速度、到达距离、终点朝向、超时和失败策略。NPC 负责地面修正、局部绕行、走路状态和真实到达；动作等待 NPC 报告完成。

### 6.2 沿固定路线

动作引用现有 TavernRoute 或后续通用 Route 提供者。路线点继续是场景树中的 Marker3D，因为作者需要在 3D 视口拖动位置和顺序。动作可覆盖本次运行的终点模式，但不会复制路线坐标到事件 Resource。

剧情队列中的一次路线默认走到终点后完成。循环巡逻仍由 NPC/Route 本身负责，不让事件队列无限占用。

### 6.3 入座、离席与显隐

座位仍负责占用、碰撞空间、固定朝向和起身落脚点。动作只请求指定角色入座/离席并等待结果。隐藏或离场必须在路线真实到达后执行，不能用固定延时猜测已经走完。

### 6.4 取消

死亡、切场、区域复位或父事件取消时，移动动作必须停止本次路线/Tween，并让 NPC 回到安全、可解释的状态。取消不能清除其他系统拥有的路线、座位或后台巡逻，也不能让迟到的到达通知继续推进事件。

## 7. 运行、并发和失败规则

1. 每条事件内部严格串行。
2. 不同事件可以同时等待触发和条件；真正需要前台控制的动作仍经过现有请求调度器。
3. 对话或商店期间触发的普通剧情事件记录事实，等前台释放后复核条件再开始。
4. 演出期间玩家再次按 E 的普通交互继续当次拒绝，不排队到玩家离开后自动弹出。
5. 纯后台动作可并行，但必须由动作类型明确声明，不能由作者随意把有界面/镜头的动作改成后台。
6. 玩家死亡立即阻止新普通动作，取消当前事件链和持续提供者，再进入死亡流程。
7. 切场获准后关闭旧场景请求；旧回调、Timer、Tween 和信号不能操作新场景。
8. REGION 事件在区域复位时取消本轮执行并清除本轮触发事实；SCENE 事件不重播。

默认失败策略为“停止当前事件并报告事件 ID、动作序号、动作类型和原因”。只有无关紧要的表现动作可显式选择“失败后继续”。切场、状态结算、Wave 生成、NPC 必须到位等关键动作不能静默跳过。

## 8. 检查器体验

在 `Event Sequences` 数组中，作者可以添加、删除、复制和拖动事件顺序；在事件的 `Actions` 数组中可以添加、删除、复制和重排动作。

添加动作使用按类别分组的选择器，例如：

```text
添加动作
├─ 流程
│  ├─ 等待
│  └─ 等待事件
├─ 角色与 NPC
│  ├─ 移动到点
│  ├─ 沿路线移动
│  └─ 入座/离席
├─ 战斗
│  ├─ 生成波次
│  └─ 等待清场
└─ ...
```

每个动作只显示自己的字段。数组折叠标题显示序号、图标/类别、动作名称和关键目标，例如 `03 角色/NPC：Runner 沿 RunnerToStaffDoor 移动`，避免全部折叠后只看到 Resource 类型名。

检查器插件只负责资源选择、折叠摘要、Undo/Redo 和即时诊断；运行时不依赖编辑器插件。关闭插件后资源仍可保存、加载和运行，只是添加体验退回原生 Resource 操作。

必须支持：

- 新建动作资源默认为场景内建资源，复制后独立，避免误改共享事件；
- 显式保存为外部 `.tres` 时提示其共享影响；
- NodePath 选择相对 SceneDirector，保存重载后保持；
- 类型不匹配的目标在检查器和运行前均给出可定位错误；
- 原生 Undo/Redo、场景保存、继承场景和实例覆盖；
- 数组空项、重复 ID、非法依赖和触发循环诊断。

## 9. 典型事件示例

### 9.1 仓库增援

```text
触发：玩家进入增援区域
条件：玩家存活；reinforcement_called 为 false
动作：
1. 关闭仓库门
2. 镜头展示增援入口
3. 请求 Wave2 出场
4. 等待 Wave2 真实生成
5. 设置 reinforcement_called = true
6. 等待 Wave2 清场
7. 开放出口
```

### 9.2 送货伙计

```text
触发：对话标签 delivery_start
条件：Opening 仍有效；伙计存在
动作：
1. 显示 Runner
2. Runner 沿入口路线到交付点
3. Runner 面向 Merchant
4. 播放放箱动作
5. 发放武器、弹药和医疗包
6. Runner 沿员工通道路线上离场
7. 隐藏 Runner
```

### 9.3 条件分支拆分

“有钥匙开门，否则提示”配置为两条事件：

- `door_with_key`：相同触发 + 拥有钥匙条件 → 开门；
- `door_without_key`：相同触发 + 不拥有钥匙条件 → 播放阻断对话。

事件内部不出现 `if/else` 或跳转。

## 10. 文件与职责建议

最终路径在实施计划中逐项确认，建议按现有 `scripts/systems` 结构拆分：

```text
scripts/systems/scene_events/
├─ scene_event_definition.gd
├─ scene_event_runner.gd
├─ triggers/
├─ conditions/
└─ actions/
   ├─ scene_action.gd
   ├─ flow/
   ├─ actor/
   ├─ combat/
   ├─ presentation/
   ├─ world/
   ├─ state/
   ├─ transition/
   └─ advanced/

addons/scene_event_inspector/
├─ plugin.gd
├─ action_picker.gd
└─ event_inspector.gd
```

现有 `scene_request.gd`、`scene_request_scheduler.gd`、`scene_pause_coordinator.gd`、各执行器和 SceneDirector 核心继续提供运行授权。新的 Action Runner 使用这些接口，不建立第二套事件总线、暂停系统或场景加载器。

## 11. 兼容迁移

迁移按可独立验收阶段进行，不一次性改写全部场景。

1. 建立新定义、动作基类、Runner 与检查器选择器，但不迁移正式场景。
2. 提供旧 SceneFlowRule/SceneFlowAction 到新运行入口的适配；保留旧脚本 UID 和已保存资源。
3. 先迁移酒馆开场的装备发放和一段 NPC 路线，验证事件队列、固定移动、取消和检查器保存。
4. 再迁移镜头、对话提示、座位和伙计离场，逐步缩小 `opening_sequence.gd` 的硬编码编排职责。
5. 迁移一个关卡的增援/清场/出口流程，确认 Wave 层级、生成约束和返程门语义不变。
6. 分别迁移其余正式场景；每完成一场才删除该场已无引用的旧配置。
7. 所有正式内容迁移并验证后，才考虑将旧大枚举标记为兼容接口；不为了代码整洁提前删除。

迁移期间，单条流程只能有一个权威入口，不能让旧 Opening 脚本和新事件同时发放装备、刷怪、切场或触发对话。适配层必须记录迁移状态和重复配置诊断。

## 12. 不在本次范围

- 可视化节点图、时间轴编辑器或通用脚本语言；
- 事件内部任意分支、循环、跳转和递归；
- 把敌人 AI 动作、玩家战斗或 NPC 寻路重写为导演动作；
- 把所有简单 Interactable Effect 强制搬到 SceneDirector；
- 修改现有五关敌人参数、装备、训练、地图或导航；
- 远端同步、场景重排或脚本 UID 迁移；
- 将事件资源自动保存为跨场共享库；首版以场景内建资源为默认。

## 13. 验证与验收

验证按改动阶段选择必要范围，不默认重复全量回归。

### 13.1 结构和检查器

- 事件/动作类型可创建、复制、删除、排序、撤销和重做；
- 隐藏字段不丢失，保存/关闭/重开后资源类型、NodePath 和参数一致；
- 内建资源不会因复制事件意外共享；显式外部资源保持共享；
- 六个正式场景仍各有唯一导演，Wave → Squad → Enemy 层级不变；
- 无效目标、重复 ID、空动作和触发循环提供明确诊断。

### 13.2 运行契约

- 线性队列严格等待真实完成，不把请求获准当作动作完成；
- 对话/商店占用时事件等待，释放后复核条件并只执行一次；
- 死亡、切场、区域复位和目标离树能取消持续动作；
- 迟到信号不能推进已取消或新一轮事件；
- 一个事件失败不破坏其他合法后台等待或暂停所有权。

### 13.3 NPC 固定移动

- 真实 NPC 沿保存路线经过路点并到达终点；
- 面向、入座、离席、隐藏和离场按真实完成衔接；
- 临时阻挡、目标缺失、路线取消、死亡和切场有确定结果；
- 取消后无残留 Tween、路线占用、座位碰撞例外或玩家输入锁；
- 日常 Patrol On Ready 和未迁移环境行为不受影响。

### 13.4 波次和关卡

- 新动作只通过导演请求 Wave，保留出生空间、导航、暂停和区域许可；
- 真实生成后才完成生成动作和播放增援镜头；
- blocked 出生继续等待，静态部署错误进入 failed；
- 清场等待使用真实 Wave 状态，五关返程门和 LevelFlow 语义不变；
- 保留 `enemy_wave_events_test`、`scene_reinforcement_test`、`level_flow_test` 等定向入口的原断言。

### 13.5 正式流程

- 酒馆开场的对话、坐席、伙计交付、装备发放与入关不重复、不漏步；
- 现有交互、商店、任务金额、检查点和切场事务保持；
- 渲染模式核对镜头、暂停、鼠标和真实 NPC 移动，不能只用 headless 证明画面与输入交接。

已有失败和本地资源差异继续按 `docs/testing.md`、`docs/enemy-tests.md` 分开报告，不修改用户参数或旧断言迁就新架构。
