# 低弹药实时掉落与可扩展弹药类型设计

日期：2026-10-26

状态：用户已要求按本文实施。功能已接入，实际配置、默认值与验证结果见[实施记录](../plans/2026-10-26-ammo-drops-and-types.md)和[使用说明](../../gameplay/AMMO.md)。以下保留设计依据及验收约束。

## 1. 已确认要求与本稿建议

用户要求：

- 玩家持有的一把武器，其总弹药少于半个弹匣后，敌人死亡会掉落该种弹药。
- 每种弹药资源直接配置掉落数量下限和上限，在该范围内随机；此要求取代最初“半个至一个弹匣”的数量换算。缺弹触发仍为总弹药少于半匣。
- 提供允许/禁止随机弹药掉落的配置，避免高级武器的弹药进入这套补给。用户允许开关放在武器或弹药类型上。
- 考虑用资源文件增加弹药种类，解决当前新增类型缺少操作入口的问题。
- 先写文档的阶段已完成；本次依据用户“按照这个改吧”的要求实施。

本轮补充确认：

- 多把武器同时缺弹时，每个敌人只掉**最缺弹的一种**。
- 弹药落在地上，玩家**靠近后自动拾取**。
- 每种弹药资源可指定掉落模型，例如不同颜色的盒子，生成时直接使用对应外观。
- 每种弹药资源独立设置掉落数量范围，不随使用它的武器弹匣容量变化。

以下规则原为本稿建议，用户要求按本文实施后采用：总量包括同类共享备弹和所有携带枪械的同类匣内余弹；缺弹程度按弹匣比例比较；掉落开关放在弹药类型资源；触发后必掉，随机的只有数量；新弹药类型默认关闭掉落、现有四类普通弹药明确开启；没有拾取的地面弹药不计入库存、不阻止后续死亡掉落。具体数值与边界见后文。

## 3. 配置方案比较

| 方案 | 收益与限制 |
| --- | --- |
| 仅给 WeaponData 加掉落开关，保留四项枚举 | 改动少，但新增弹药仍要改代码；同类武器共享备弹时，单枪禁用也不能隔离高级武器获得的补给 |
| **弹药类型资源＋类型掉落配置（建议采用）** | 一份资源定义名称、稳定标识、掉落开关、数量范围和模型；武器引用它，新增种类无需扩枚举；同类共享规则一致 |
| 增加通用战利品表、权重和稀有度系统 | 可做更多物品掉落，但超出此次“缺弹补给＋弹药扩展”的需求，留待另行提出 |

建议只提供弹药类型这一个掉落开关，避免武器和弹药各放一个相互覆盖的开关。若高级武器使用独有弹药，为它建一个禁止掉落的新类型；若它与普通枪共用相同类型，普通枪捡到的备弹本来就能给它使用，这属于共享弹药规则，不能靠武器名字或外观区分。

## 4. 缺弹与掉落规则

### 4.1 死亡时读取实时库存

以每次真实敌人死亡为机会，同步读取所在区域当前存活玩家的 Equipment。检查两个携带槽，包括收起的枪；不检查未携带武器，不依赖玩家当前拿着哪把枪，也不依赖死者自己的武器或弹药种类。

当前项目按单玩家设计。没有本区存活玩家、区域未激活、世界暂停/对话中、实例只是被卸载或复位时，不产生掉落。现有死亡信号没有击杀者对象，本稿按“本区敌人实际死亡”处理，不额外要求最后一击必须来自玩家；若以后需要击杀归属，应单独扩展伤害事件，不能拿攻击位置推断身份。

对一种弹药 `a`：

```text
N(a) = 该类型共享备弹
     + 两个携带槽中，使用该类型的所有有效武器的匣内余弹

C(w) = 被检查武器的弹匣容量
缺弹条件：2 × N(a) < C(w)
缺弹程度：N(a) / C(w)，越小越缺
```

- 共享备弹只加一次；两个槽即使引用同一个 WeaponData，也分别计入各自真实弹匣。
- 尚未初始化的有效槽按现有出生满匣规则计数，查询不偷偷装备武器或创建新弹药。
- 正在换弹/保留50%阶段不额外增加或减少总量。逐发装填已完成的弹药只从备弹移到弹匣，不重复计数。
- 恰好半匣不触发；容量1只在总弹药0时触发。无枪、专用近战或无效弹药定义不参与。
- 地面尚未拾取的弹药不是玩家库存，暂不计入 `N`。本稿不额外添加冷却、累计额度或未拾取包限额；因此不捡时后续击杀仍可掉落。这是规则边界，不隐含“地上已有弹药就算玩家已有”。

### 4.2 每次只选一种

只保留弹药资源允许掉落且满足缺弹条件的武器。同一弹药类型合并成一个候选：选择该类型携带武器中容量最大的枪作为缺弹判断的参考，等价于选择同类中最缺的比例；不会同时给同类主副枪各掉一包。参考容量只影响触发和缺弹程度，不参与掉落数量计算。

不同类型比较 `N / C`，选择比例最低的一种；相同比例按主槽优先、副槽其次，保证结果稳定。不是绝对剩余发数最少，也不按当前手持槽优先。类型被禁用后，从剩余合格类型中重新选择。

### 4.3 数量与随机数

```text
最小量 = AmmoDefinition.drop_min_count
最大量 = AmmoDefinition.drop_max_count
本次数量 = 上述闭区间内均匀随机的整数
```

上下限均为整数，要求最小量至少1、最大量不小于最小量；两者相等表示固定数量。范围可以小于半匣或大于一匣，完全由该弹药资源配置，不按武器容量裁剪、换算或取整。无效范围在配置处给诊断，并暂不让该类型参与掉落，避免生成0发包或暗中交换上下限。

本次采用的弹药类型、数量范围、模型引用和最终数量在死亡时一次确定，之后切枪、修改配置或波次清理不重新抽取；延迟生成使用已确定的外观引用。随机数单独持有，不能扰动原弹道、爆头或 AI 随机序列。

触发后没有第二次“掉不掉”的概率门槛。用户所说的随机掉落在此解释为随机数量；以后若需要掉落率再单独增加配置。

| 例子 | 判断与结果 |
| --- | --- |
| 12发手枪，匣内2＋备弹3，该类配置掉4～8发 | 总量5，小于6；掉4～8发 |
| 同一把手枪，匣内3＋备弹3 | 总量6，恰好半匣，不掉 |
| 5发武器，总量2，该类配置掉2～4发 | 小于2.5；掉2～4发，不按半匣取整 |
| 手枪12发/余量3，霰弹2发/余量0，霰弹配置掉3～5发 | 比例0.25与0；只掉霰弹3～5发，即使超过当前枪一匣 |
| 两枪同类，容量12与30，匣内合计4＋共享备弹2，该类配置掉8～16发 | 总量6，按30发枪满足缺弹；只掉该类8～16发 |
| 高级武器弹药允许掉落为关闭 | 不成为候选；仍可正常携带、射击、换弹及读取手工配置的初始备弹 |

## 5. 弹药类型资源与操作入口

建议新增 `AmmoDefinition` 资源，路径 `scripts/weapons/ammo_definition.gd`；实例放在 `resources/ammo/types/`。字段名与以下默认值属于实施建议：

| 字段 | 用途与建议初值 |
| --- | --- |
| `ammo_id: StringName` | 稳定唯一标识，例如 `pistol`、`shotgun`、`energy_cell`；不以资源文件名或显示名称作库存键 |
| `display_name: String` | 检查器、地面标签和拾取提示用名 |
| `allow_random_drop: bool` | 是否参与本套缺弹掉落；新建类型默认false，普通四类预设明确设true |
| `drop_min_count: int` | 每份最少弹药数，至少1；新建类型建议默认1 |
| `drop_max_count: int` | 每份最多弹药数，不小于下限；新建类型建议默认1，与下限相等即固定数量 |
| `drop_model: PackedScene` | 该类型的掉落外观场景，根节点为Node3D；例如蓝色手枪弹盒、红色霰弹盒。未指定时用通用盒子 |

数量范围和模型是静态配置；本阶段不往资源里保存库存、本次抽取的数量或概率进度，也不为尚未提出的弹种效果添加伤害、穿甲等字段。四类普通弹药的范围需分别明确填写，文中4～8、3～5等仅为说明示例，不是用户已确认的平衡数值。

WeaponData 在原“射击与弹药”组增加 `ammo_definition: AmmoDefinition` 资源框，展开即可修改类型、掉落开关、数量范围和模型。弹匣容量仍由武器决定，仅用于缺弹判定，不决定每包数量。该字段不是射击模式，霰弹图样和逐发装填继续由原 Shotgun 资源负责。

### 掉落模型配置

在弹药资源的 **掉落外观 → Drop Model** 拖入一个模型场景。初版可提供不同颜色的盒状场景放在 `scenes/presentation/ammo/`：用普通 BoxMesh 和各自材质区分弹种，后续可换成正式弹药盒模型，掉落代码无需按弹种分支。具体颜色属于美术建议，名称/数量标签继续保留，识别不只依赖颜色。

模型场景只包含外观，不携带拾取脚本、库存、Area3D或阻挡碰撞。通用 `ammo_pickup.tscn` 在自己的 `Visual` 子节点下实例化模型，统一管理位置、名称、数量及拾取检测。模型原点以底面中心为基准，尺寸和朝向在模型场景内调整；更换或缩放模型不改变拾取范围。

每个弹药包创建独立的外观节点，不能通过修改共享材质给当前包临时染色，否则可能把其他类型的包一起改色。不同颜色可直接保存为不同模型场景/材质资源，运行时不重写它们。模型未配置、加载失败或根类型不合要求时，显示通用盒子及该弹种标签，继续正常领取，不生成不可见补给。

Equipment 的“初始共享备弹”改为可添加的资源条目列表：每项 `AmmoSupply` 包含弹药资源引用与非负数量。条目为出生配置，不是运行库存。未列出的新类型初始备弹0，但装备的枪仍按原规则满匣出生；显式0也必须保留，不能被默认36覆盖。

### 新增一种弹药的预期操作

1. 在 `resources/ammo/types/` 新建 `AmmoDefinition`，保存为如 `energy_cell.tres`。
2. 填写唯一 `ammo_id`、显示名称、是否允许随机掉落，以及最少/最多掉落数。
3. 在 **Drop Model** 指定该类型的盒子或正式模型场景；可直接预览模型场景并调整颜色与尺寸。
4. 在使用它的武器资源中，将它拖入 **射击与弹药 → Ammo Definition**。
5. 如需出生备弹，在 **Player → Equipment → 初始共享备弹** 增加该类型条目和数量。
6. 多把枪共享弹药时引用同一类型资源，其掉落范围和模型也共用；新增真正不同的种类时创建新ID。仅修改文件名不会创建新种类。

无需新增枚举项、全局自动加载器或扫描整个项目的弹药注册表。配置检查只检查实际引用集合：空ID、重复初始条目、同ID但掉落开关/数量范围/模型定义冲突给明确诊断，不静默覆盖。资源深复制后同ID且定义一致仍视为同类；模型按其资源身份比较，不按某次实例节点比较。初始条目重复不叠加免费库存，建议保留第一项并报告错误，修正后重开。同ID定义冲突时不拆出第二份库存，并暂停该类型的自动掉落，避免任意选择一份定义。

弹药ID、武器类型引用及初始库存的配置修改在重开后生效；当前运行中的弹药状态绑定已解析的类型键，不能通过热改资源ID把一类余弹变成另一类。拾取包保存生成时的ID和数量，不在领取时重新解释为别的类型。

## 6. 库存接口与旧资源兼容

建议新增公开查询/补给接口，具体签名在实施时随现有接口约束核对：

- WeaponData：`get_ammo_definition()` / `get_ammo_key()`，只解析静态类型，不保存弹药运行状态。
- Equipment：`ammo_snapshot()`，一次返回两槽武器、弹匣容量、匣内弹量与同类共享备弹；只读且不切枪。
- Equipment：`add_ammo(ammo_definition, amount) -> int`，返回实际加入备弹的数量；成功后通知原 HUD。只加备弹，不直接补满弹匣、不自动换弹、不重置换弹进度。
- WeaponAmmo：沿用原消耗/换弹接口，通过统一类型键读写原共享池。

运行备弹池建议统一以 `ammo_id` 为键。旧整数 `ammo_type` 0/1/2/3 保留兼容解析，映射到四份规范资源；不重排枚举、不用改名后的显示文本匹配。新增显式资源优先于旧整数；显式资源存在却无效时必须诊断，不能悄悄变成默认手枪弹药。

旧四个 `starting_*_ammo` 保存字段保留加载兼容。新列表按类型覆盖旧值：未显式配置的旧四类继续采用该场景的原保存初值；新列表配置0则覆盖为0。编辑入口展示解析后的初值，避免同时显示两套可互相覆盖的配置；另存后的新配置以资源列表为准。实现前应验证 Godot 资源加载、检查器撤销和场景继承覆盖顺序，不能靠每帧写回资源迁移。

旧测试中直接按整数下标访问 `reserve_ammo` 的夹具需要迁到统一类型键/公开接口，仍保留原数值、扣弹、共享、暂停和重开断言；不能通过删除兼容用例掩盖旧资源加载失败。迁移期间不混用两种库存键或复制两份余额。

实际保存的武器和场景以用户本地配置为基线，先支持旧资源自然解析，再做用户可见的配置迁移；不顺带覆盖当前武器弹量、换弹时长或其他调参。敌人继续有限弹匣、无限备弹，不从玩家掉落池补充，也不因新增类型改变 AI 规则。

## 7. 死亡接入、掉落实体与自动拾取

建议区域持有一个 `AmmoDropController`（`scripts/world/ammo_drop_controller.gd`，可用 RefCounted），由原 `register_enemy()` / `unregister_enemy()` 接入死亡信号。它只编排候选、随机数量和生成，不持有玩家库存，不进入团队协调器或个人 Utility。

```mermaid
flowchart LR
    A[敌人真实死亡] --> B[区域检查本轮事件与玩家]
    B --> C[Equipment 实时库存快照]
    C --> D[选最缺的一种允许掉落的弹药]
    D --> E[确定数量并生成地面弹药]
    E --> F[玩家靠近且可拾取]
    F --> G[Equipment 增加对应备弹]
    G --> H[更新 HUD 并销毁已拾取包]
```

死亡回调内先确定类型、数量、模型引用和死亡位置；物理帧不允许直接改节点时，只延迟生成实体。延迟任务携带区域本轮代际、冻结的结算值和外观资源引用，不能到稍后重新读取已经被回收的死者或重新查询弹药类型的模型字段。每个敌人每次生命只受理一次；重置后是新生命。注销、重复信号、波次退树和尸体外观替换不额外掉落。

实体建议为 `scenes/world/objects/ammo_pickup.tscn`，脚本 `scripts/world/ammo_pickup.gd`，包含装载弹种模型的 `Visual`、名称/数量标签和玩家检测 Area3D。独立挂在所属区域的内部掉落容器下，不挂在敌人、Squad、EnemyWave 或尸体下；不增加阻挡角色、枪线或导航的实体碰撞。拾取与数量结算始终由通用根节点执行，各颜色盒子只作为其外观子节点。

生成位置取死亡处附近的本区合法地面；普通地面优先原位置，翻越中或墙边死亡时做有限的附近地面/可达性检查。不得放进墙内、掩体顶上或另一楼层，也不自动传送到玩家脚下。附近找不到合法落点时不凭空加库存，保留一次诊断；落点搜索预算和容差在实施专项中确定。

靠近拾取建议半径0.8米，并校验同层及无实体墙阻挡，防止隔墙/隔层拾取；此半径为建议初值，不是用户固定要求。仅存活、非对话、非暂停的本区玩家可以领取。进入范围时先置领取状态，再调用 `add_ammo()`，成功后消费对应数量，防止同帧重复入账；失败不销毁。若玩家已在范围内但当时不能领取，恢复资格后要能继续领取，不能只依赖一次 `body_entered`。只对有附近玩家的包进行低频重试，不扫描全地图。

已经生成的包保持原类型和数量，拾取时不再检查是否低于半匣、不因后来弹量恢复而作废。允许存入同类型备弹，即使此刻换了手持槽；拾取不会改变枪内余弹、当前枪械、后坐或开火冷却。提示如“手枪弹药 +8”，由真实入账结果触发。

## 8. 生命周期与幂等

| 情况 | 预期行为 |
| --- | --- |
| 同枪多弹丸致死、普通致死、爆头秒杀 | 都只沿真实 `died` 生成一次 |
| 重复注册/死亡通知 | 不重复绑定，不重复生成或入账 |
| 一枪杀死多个敌人 | 每个死者各有一次机会，按事件发生时真实库存判断；没有拾取就不会预先记入库存 |
| 最后一个敌人死亡、波次清空、下一波出现 | 已生成的包保留；延迟生成也不能被旧波退树吞掉 |
| 暂停或对话 | 不拾取；恢复后附近包可以继续领取 |
| 最后玩家离开区域、区域复位/卸载 | 清理该区域地面包及待生成请求，旧代际回调无效 |
| 玩家死亡并重新开始 | 仍按现有场景重开恢复初始装备/库存；不把战斗弹药写入持久 GameState |
| 靶子受击、敌人仅被卸载或换波取消 | 没有真实敌人死亡就不掉落 |

掉落服务的复位跟随原区域复位入口，不能借 `presentation_reset` 的表现语义隐式维护库存；可以在同一复位流程显式清理包与死亡去重记录。区域退出也清理信号和待生成请求，避免绑定旧实例。

## 10. 实施前的验收清单

以下清单作为实施约束保留；实际执行的检查及旧测试限制见实施记录，不把清单本身当作通过证据。

1. **数量边界**：触发覆盖容量1、奇数、偶数及半匣以下/恰好半匣/以上；数量按弹药资源上下限，最小等于最大、超过一匣和小于半匣均正确，负数/0/反向范围有诊断。同类换用不同容量武器不改变数量范围；抽样始终为闭区间整数，独立于弹道和爆头。
2. **库存真实**：共享池只计一次、同资源双槽独立弹匣、未切到的满匣、收起枪、空槽、近战；普通/逐发换弹和半程中断不会改变总量或重复扣补。
3. **选一种**：两类同时不足按比例选最缺，同类合并、不同容量、平局规则、当前手持槽无偏置；禁用类型绝不掉落。
4. **扩展与兼容**：仅新建一个资源就能加入第五种弹药，正常射击/换弹/共享/拾取/HUD；旧四类编号、旧初值、显式0、保存重载、继承覆盖和撤销仍正确；冲突配置给可定位诊断。
5. **真实死亡链路**：玩家实际射杀、霰弹多弹丸、爆头、同枪多人及最后一人；每死者每生命最多一次，不能只调用掉落选择函数冒充运行验收。
6. **真实拾取**：生成在可达地面，真实玩家靠近入账；没有重复领取、不隔墙/隔层、不直接补匣；对话/暂停时不拾取，恢复后无需重新走出走入。
7. **波次与重开**：静态敌人和波次敌人都有效；最后一人掉落跨波保留；离场清理、重开恢复、待生成回调跨代际失效；没有退出泄漏或失效对象访问。
8. **原回归**：沿现有弹药、双槽、玩家换弹、半程换弹、逐发装填、霰弹、爆头及敌人换弹专项；修改整数库存夹具时保留原断言含义。登记新增专项与文件清单，不放宽已有行为门槛。
9. **资源外观**：不同弹种各实例化指定模型，同时存在时颜色/材质不串改；替换模型、尺寸调整不改变拾取范围或弹药量；空模型与无效根类型使用可见备用盒子。模型引用及数量范围支持资源保存重载，旧包保留生成时的模型选择。

实施按资源与兼容、实时需求与死亡、实体拾取及生命周期的顺序完成；本阶段代码、操作说明和验证记录一并审查提交。用户原武器、图样、地图与训练调参保留。
