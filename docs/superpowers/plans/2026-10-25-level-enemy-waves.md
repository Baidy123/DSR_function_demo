# 通用关卡敌人波次系统构建计划

编写日期：2026-10-25。

状态：待实施。本次只编写计划；尚未增加运行脚本、改变关卡部署或完成波次功能验收。

## 1. 用户方向与范围

用户已明确：

- 面向所有 `lvl` 共用，不能写成只适用于 `lvl_1` 的脚本；第一关可作为首个接入示例。
- 在场景中提前摆好各波小队和敌人，通过场景与检查器调整位置及配置。
- 一波可以包含多个小队；本波所有敌人死亡后，才允许生成下一波。
- 场景本身保存部署配置，省去原先考虑的 JSON 名单，不维护两份敌人配置。
- 刷新位置由人规划，只需要适度的占位保险，避免把这一部分做得过于复杂。
- 尽量减少不必要的测试；新增检查器参数需要注释说明用途、单位及实际行为。

本计划采用的实现建议，尚不作为用户逐项确认的规则：

- 使用固定的人工部署点；生成前检查占位，被占用时等待重试，保持原部署位置。
- 整波部署检查通过后再一起生成，避免一部分已参战、另一部分仍堵在刷新点。
- 首波随玩家进入本区域启动；最后一名玩家离场时重置到首波，沿用现有区域的入场／离场习惯。
- 波间延迟默认0秒，可以在检查器调整。暂停、玩家死亡或对话期间不推进生成等待。
- 最后一波清空只发出完成信号；胜利界面、剧情跳转和存档不在首版范围内。

## 3. 场景编辑方式

新增共用 `EnemyWaves` 节点，在它下面按场景树顺序排列波次；名称用于识别，顺序以树中排列为准，不再另存一份数字波次名单。

```text
LvlN                         原 shooting_range.gd，保留根路径
├── Player / Camera3D        已有角色与镜头，按本关配置保留
├── CombatZone               原区域路径
├── NavigationRegion3D       原导航及地图实体
└── EnemyWaves               共用波次控制器
    ├── Wave1                波次配置节点
    │   ├── SquadA           原 squad.tscn 实例
    │   │   ├── Enemy        原敌人／兵种预设实例
    │   │   └── Enemy2
    │   └── SquadB
    │       └── Enemy
    └── Wave2
        └── SquadC
            ├── Enemy
            └── Enemy2
```

编辑时所有波次均可见。直接拖动现有小队和敌人，调整朝向、血量、武器、Training 与小队 Profile；波次节点只管理部署与时间，不再复制这些敌人参数。

已有地图兼容：第一关现有 `Lvl1/Squad` 保持原路径和内部节点。在 `Wave1` 的“引用已有小队”中选中这个节点，作为第一波部署；后续新增小队可以放到相应波次节点下。引用只指向场景中已有的小队，不另存成员或坐标。同一个小队只能被一个波次管理，不能重复生成。

新建地图优先使用示意中的直接子小队结构。“引用已有小队”用于保留已有路径，也允许复用已经在地图中摆好的小队；两种写法经过同一个部署收集和生成流程。

共享资源语义保持：只改某只敌人的普通节点属性是实例覆盖；展开共享武器／训练资源修改内容仍影响其他引用者。波次系统不得自动改写原 `.tres`，也不得在后台给共享资源写入生命、波次或进度。

### 检查器入口

| 节点 | 拟定属性 | 建议初值 | 说明 |
| --- | --- | --- | --- |
| EnemyWaves | `auto_start_on_enter` | true | 玩家进入所属 CombatZone 后启动首波；关闭时由明确的 `start_encounter()` 调用启动。 |
| EnemyWaves | `spawn_retry_seconds` | 0.25秒 | 刷新点被占用后的重试间隔；必须大于0，避免每帧反复扫描。 |
| WaveN | `start_delay_seconds` | 0秒 | 到达这一波条件后，生成前的等待时间；首波也可使用。 |
| WaveN | `existing_squads` | 空 | 可选 NodePath 列表，引用同区域中已经摆好的小队；不包含逐个敌人的第二份配置。 |

每个导出属性添加中文 `##` 注释，说明单位、0的含义及修改效果。配置不完整、重复引用、引用跨区域、空波次及小队结构错误应给出清晰诊断；不静默跳过错误波次或自动宣布完成。

## 4. 模板与实际参战实例

建议采用“运行树之外保留部署模板，轮到时复制为运行实例”的方式，保持普通场景编辑体验，避免增加自定义编辑器插件或额外名单资源。

1. 区域根在 `_enter_tree()` 阶段找到可选 `EnemyWaves`，在任何受管理 Squad／Enemy 子树入树前，调用部署捕获入口。
2. 保存原小队的父节点、名称、局部变换和完整配置子树，将它们收存在运行树之外。场景编辑模式不执行这一步。
3. 模板只作为本次运行的配置来源；不接入区域服务、碰撞世界、目标／近弹列表或 AI 循环。
4. 某波可以生成时，从未运行的模板复制新的小队实例，在入树前设置最终部署变换和死亡订阅，再加入原部署父节点。保留预摆放形成的相对位置、朝向和既有节点路径。
5. 原 Squad／Enemy 的正常入树和就绪流程自行完成装配及注册，波次控制器不直接调用 AI 的 `_ready()`，不向协调器注入目标或任务。
6. 清理运行副本时沿原退树注销流程释放；重开／离场后再次从原模板生成，不能复制已经受伤或移动过的敌人。
7. 释放关卡时同时释放树外模板，避免遗留孤立节点。跨区域重新挂父节点不作为波次切换手段。

这一技术路线必须先做最小验证：父级捕获确实早于所有受管理子树的入树；复制确实保留实例覆盖、嵌套 Training／Weapon 引用、小队 Profile、资源本地化及内部节点。不得直接用 `PackedScene.pack()` 假定能保存父关卡拥有的全部后代；`owner` 不符合要求时可能漏掉手工添加的成员。也不得以“启动后隐藏／关闭处理”替代模板隔离。

以上属于拟定实现，当前尚未验证。阶段1先证明可行性；如引擎时序或复制规则不能满足，先记录具体失败并调整模板捕获实现，不能擅自改成要求用户另维护 JSON、手填敌人属性或拆分每一波文件。

引擎依据：[Godot Node 文档](https://docs.godotengine.org/en/stable/classes/class_node.html)说明父节点先执行入树回调、子节点随后进入；节点复制、场景所有权与移出树后的释放责任仍需结合本项目实际预设验证。文档说明不替代本机 Godot 4.7.2 的上述实测。

模板会随关卡载入而存在于内存中，但尚未进入运行树；本方案不承诺后续波次完全不占内存。真正参战的运行副本在轮到该波时才创建并入树。

## 5. 按波次推进与清理

控制器只持有本区域的波次状态、运行副本和存活集合，不负责 AI 决策、身体移动或伤害。

建议状态为：等待启动 → 波前等待 → 等待刷新点 → 正在生成 → 本波战斗 → 下一波／全部完成。另有复位与配置错误状态，不能把它们作为清波事件。

### 生成与死亡统计

1. 启动时确定按树顺序排列的波次，以及每波的小队／成员模板；不扫描全地图的 `combat_target` 来决定本波人数。
2. 波前等待结束后检查区域和导航就绪、刷新位置及运行资格；所有部署点通过后才提交本波。
3. 在入树前收集这次运行副本的成员身份并连接 `died`，建立本波存活集合；生成完成之前，即使集合暂时为空也不能清波。
4. 一波内所有小队同时纳入统计。死亡回调按实例身份去重，最后一人死亡只安排一次后续状态切换。
5. 波次切换延迟到当前死亡回调结束后的安全时机；复核状态与本轮标识，避免同帧多人死亡、旧信号或退出回调重复刷下一波。
6. 只从收到真实死亡的成员集合中减员。尸体未释放不阻止清波；意外移除仍活着的敌人属于异常，给出诊断并停止推进，不伪装成被击杀。
7. 上一波运行根销毁并完成注销后，才提交下一波；不让旧协调器、预约、近弹监听或导航成员带入下一波。
8. 最后一波清空发出一次完成信号并停止推进；不自动循环或跳转场景。

### 固定刷新点的基础保险

按用户最新补充收敛：不增加自动找附近位置、随机偏移、刷新区域搜索、强制推开玩家或重排队形的系统。人工规划的位置保持不变。

- 生成检查包含玩家、现有敌人、墙体与其他真实身体，按实际敌人胶囊及碰撞掩码检查完整身体空间，不只检查脚底点。
- 同波待生成成员还没有进入物理世界，必须额外检查它们相互之间的占位；不能因为物理查询没有看到对方就把两只刷到同一点。
- 沿用所属区域已有地面／导航合法性要求，等待地图与本区域同步；不借此次功能重烘导航，也不引入新的自动寻路选点。
- 人工部署点被玩家临时占住时，整波保持“等待刷新点”，按重试间隔再次检查；玩家离开后再正常生成。
- 等待期间不扣除待生成人数，不发清波／完成信号，不跳过小队，不超时强刷。长时间受阻只保留清晰的 Debug 原因，避免每次重试刷屏。
- 提交生成前再次核对占位；失败则取消本次提交，不留下部分已入树成员。生成本身安排在物理查询允许的安全时机。
- 明显的静态摆放错误由编辑器／启动诊断指出，需要人工修改；基础保险不承担自动修正地图设计的职责。

不得复用默认排除玩家的 AI 候选检查来判断刷新安全。优先在波次脚本内用区域的物理空间与模板胶囊做小范围只读查询，保持现有通用身体、感知与导航接口的职责。

### 区域离场、暂停与重开

- 区域仍是唯一玩家进出判定者。控制器通过区域的启动、推进与复位入口工作，不另设一套全地图玩家检测。
- 普通波间等待及刷新重试只在区域有效、玩家存活且可运行时计时；暂停、死亡界面和对话不推进。对话结束后接续剩余等待，不重新开始整波。
- 最后一名玩家离场：先使波次本轮标识失效、停止待生成和延迟任务、断开本轮死亡订阅，再安全销毁运行副本并清空统计，回到等待首波。
- `shooting_range.gd._reset_targets()` 在收集旧目标之前处理波次复位，并排除所有正在清理的波次实例；不要对仍等待延迟释放的敌人调用 `reset_target()`。
- 原区域服务和 `presentation_reset` 通知仍只清理一次。无波次组件的地图／竞技场继续走现有复位流程，不复制区域服务实现。
- 玩家重开沿原重载当前场景处理；所有树外模板、旧信号、延迟任务和运行副本都随原关卡释放。两个区域的控制器互不推进、互不清理。

控制器拟定公开入口：

- `capture_templates(region)`：由区域在受管理子树入树前调用，完成一次配置捕获。
- `start_encounter()`：仅等待启动状态有效，重复调用不能重复生成。
- `advance_from_region(delta)`：推进本区域有效时钟中的等待与重试。
- `reset_encounter()`：取消本轮并释放运行副本，不等同于清波。
- `owns_runtime_enemy(enemy)`：区域复位排除波次实例使用，清理尚未完成时也有效。
- `debug_snapshot()`：只读当前波、状态、存活／待生成人数和阻塞原因。

拟定信号：`wave_started(index)`、`wave_cleared(index)`、`encounter_completed()`；受阻诊断通过只读状态提供，不把每次重试作为新事件。

## 7. 实施阶段与验收

### 阶段1：证明模板隔离与保留配置

1. 新增共用配置节点和控制器最小骨架，接入区域早期捕获。
2. 用实际 Squad／Enemy 预设和场景实例覆盖验证捕获、复制及释放；覆盖普通子小队和第一关已有 Squad 引用两种写法。
3. 在正式推进前证明：未来波次未执行入树／就绪、未注册、无真实碰撞、未加入运行树的目标和近弹列表；生成副本才正常注册。
4. 核对每个成员的血量、武器、Training、Profile、局部／世界位置与朝向，尤其是本地覆盖和共享／本地资源语义。保存重开编辑场景后部署仍然存在。
5. 将必要断言集中登记到新专项；不为了模板方案改造所有敌人脚本或新增编辑器插件。

验收：提前隔离及配置完整性确实成立，销毁后没有树外模板泄漏。此阶段不能宣称波次战斗已完成。

### 阶段2：按全灭推进与区域生命周期

1. 实现整波生成、成员死亡集合、一次推进及最终完成信号。
2. 实现本轮标识、重复事件拒绝、失败状态及安全清理；任何生成失败都不能造成跳波。
3. 接通入场、离场、暂停／对话和玩家重开，清理旧的区域自动复活路径对波次实例的影响。
4. 第一关添加控制器，第一波引用用户现有 Squad；新增后续示例小队只作为波次功能示范，不调整已有战斗参数和地图布局。

验收：第一波最后一人死亡前没有第二波运行实例；同波多个小队都计入；最后一波只完成一次。离场／重开后恢复首波，没有复活旧波、重复注册或陈旧回调。

### 阶段3：加入固定点占位保险

1. 加入实际胶囊的静态／动态占位查询和同波成员排重，生成提交前复核。
2. 使用同一个状态流程等待重试，保留人工部署坐标；不新增自动选点、推开或超时强刷。
3. 在实际物理运行中让玩家站在第二波刷新位置，清掉第一波，确认第二波不重叠生成；玩家让开后，第二波只生成一次且位置不变。
4. 用一处墙内错误点与一组重叠成员确认诊断及不误清波；复用同一夹具，不建立完整自动选点测试矩阵。
