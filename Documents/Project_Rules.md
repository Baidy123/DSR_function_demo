# 项目规则（Project Rules）

> 本文件是本仓库的最高约束。任何 Agent 或协作者在修改代码、资源、文档之前，必须先读完本文件与 `Documents/Agent_Mem.md`。
> 若规则与实际需求冲突，先在 `Agent_Mem.md` 记录冲突，再采用“最小改动 + 可回滚”的方案执行。

---

## 1. 项目定位

| 项目 | 内容 |
| --- | --- |
| 作品名 | 《余烬自由城》 / **Ember of Free City** |
| 类型 | 2D 俯视角像素风叙事动作 RPG（单机 Demo） |
| 主题 | 接入、归属、灰色生存；自由城的霓虹与制度性排斥 |
| 输入 | `Documents/场景剧本.docx`（唯一原始设定，角色设定必须保护） |
| 产出 | 一个可在较新 Windows 上直接运行、无需安装环境的单文件 `Target.exe` |
| 体验时长 | 20–30 分钟（含探索、对话、商店、一场战斗、结局） |
| 技术栈 | C++17 + Win32 + Direct3D 11 + 自研 2D 渲染/音频/资源管线 |
| 构建 | MinGW-w64（x86_64-win32-seh-rev0 16.1.0）+ GNU Make |

### 1.1 Demo 目标（Definition of Done）

1. 从标题界面进入游戏，完成“酒吧委托 → 铁港仓库取货 → 遭遇公司特工 → 返回酒吧交差”的完整闭环。
2. 四名原始角色（小明、大美、东子、小帅）均有符合原剧本性格的对白与可辨认的像素形象。
3. 商店、支线（点唱机零件）、战斗、任务日志、结局界面可用。
4. Release 产物为单个 `Build/Release/Target.exe`，双击可玩，不依赖 DLL 安装或外部资源文件。
5. `Tools` 下至少有一个无头单元测试工具与一个离屏截图工具，且均已登记在 `Tools/README.md`。
6. 所有文档、源码、构建脚本遵循本文件的命名、注释、编码与换行规范。

### 1.2 非目标（本阶段不做）

- 不做联网、存档云同步、多语言切换、手柄支持。
- 不做开放世界与完整城市模拟；Demo 只包含三个可玩场景。
- 不引入任何第三方运行时库或需要安装的引擎。

## 2. 创作边界（最高优先级）

1. **原始角色设定不可改写**：姓名、身份、背景、性格、动机、人物关系必须与 `场景剧本.docx` 一致。
2. 允许扩展的部分：世界观细节、城市地理、组织名称、科技名词、敌人类型、支线事件、视觉设计。
3. 若扩展内容与原文冲突，以原文为准；冲突处必须在 `Agent_Mem.md` 中登记。
4. 剧情基调保持“克制的赛博黑色”：不煽情、不说教；通过环境、交易和短对白表达制度性困境。
5. 不添加与原文气质不符的要素（例如魔法、无厘头搞笑、过度血腥）。

## 3. 目录结构

```text
./
├─ Components/                 # 最终产物的功能组件块
│  ├─ Main/                    # 程序入口、窗口生命周期编排
│  ├─ Shared/                  # 基础类型、数学、字符串、随机数、日志
│  ├─ Platform/                # Win32 窗口、输入、计时、内嵌资源读取
│  ├─ Render/                  # D3D11 设备、SpriteBatch、文字纹理、后处理
│  ├─ World/                   # 地图、格子碰撞、场景定义与加载
│  ├─ Game/                    # 玩家、敌人、战斗、交互、对话、任务、商店、UI
│  └─ Audio/                   # 程序化音乐与音效（waveOut）
│     └─ Inc/ + Src/           # 每个组件必须有 Inc 与 Src
├─ Documents/                  # 规则、记忆、设计与验收文档
├─ Resources/                  # 美术资产、美术生成器、内嵌资源脚本
│  ├─ Art/                     # 可直接查看的 PNG 资产（人工审阅用）
│  ├─ ArtGen/                  # C++ 像素美术生成器（构建期工具，不进入游戏）
│  ├─ ArtPack.bin              # 运行时使用的二进制资产包
│  └─ Resources.rc             # windres 资源脚本
├─ Tools/                      # 验证工具（独立 Makefile，编译型）
│  ├─ UnitTests/
│  ├─ OffscreenTest/
│  ├─ Makefile
│  └─ README.md
├─ Temp/                       # 临时文件（不入库）
├─ Build/                      # 最终产物（不入库）
├─ Makefile                    # 只构建最终产物
├─ .gitattributes
└─ .gitignore
```

### 3.1 目录硬性规则

- `Components/<组件>/Inc` 放头文件，`Components/<组件>/Src` 放源文件。
- `Tools/` 下每个工具同样具有 `Inc/` 与 `Src/`；工具构建产物放在各自的 `Build/`。
- `Tools/Makefile` 独立于根 `Makefile`；根 `Makefile` 永远只负责最终游戏。
- `Tools/` 只接受“源码 + 自有 Makefile”的编译型工具；禁止放入脚本型测试。
- 临时输出、截图、下载缓存一律放 `Temp/`，禁止写入 `Tools/` 或仓库根目录。

## 4. 文件与命名规范

1. 源文件、头文件、资源文件名禁止出现空格；仅使用 ASCII 字母、数字、下划线。
2. 文件名以组件名作前缀，例如 `Render_SpriteBatch.cpp`、`Game_Quest.hpp`。
3. 常用缩写保持大写：`UI`、`HUD`、`D3D11`、`FS`、`NPC`、`SFX`、`AABB`、`PNG`、`ID`。
   - 正确：`Game_UI.cpp`、`Render_D3D11.hpp`、`Game_NPC.hpp`
   - 错误：`Game_Ui.cpp`、`Render_D3d11.hpp`、`Game_Npc.hpp`
4. C 头文件 `.h`，C 源文件 `.c`；C++ 头文件 `.hpp`，C++ 源文件 `.cpp`。本项目的游戏代码全部使用 C++。
5. 每个头文件必须使用如下保护宏，格式固定为“文件名全大写 + 双下划线”：

```cpp
#ifndef __GAME_QUEST_HPP__
#define __GAME_QUEST_HPP__

// ... 业务代码 ...

#endif // __GAME_QUEST_HPP__
```

6. 宏定义、枚举常量必须为全大写字母 + 下划线，例如 `MAX_ENEMY_COUNT`、`SCENE_ID_BAR_INTERIOR`。
7. 类名使用大驼峰（`SpriteBatch`），函数与变量使用小驼峰（`DrawSprite`、`currentHealth`），成员变量以 `m_` 前缀。
8. 常量使用 `constexpr`，禁止魔法数字散落在业务代码中；集中放在对应组件的常量区或配置结构体中。
9. 中文文本只出现在数据、文档和注释中；标识符、资源名、文件名一律 ASCII。

---

## 5. 代码规范

1. 标准：C++17；单文件不依赖第三方库；不使用异常做流程控制。
2. 所有权：优先 RAII；D3D 对象使用 `Microsoft::WRL::ComPtr` 或自定义 Release 封装，禁止裸 `new/delete` 管理长期资源。
3. 解耦：渲染层不包含玩法逻辑；玩法层不直接调用 D3D API；平台层只暴露窗口/输入/资源读取接口。
4. 头文件最小化：能用前置声明就不 include；禁止在头文件中定义全局对象。
5. 每个公开函数、结构体、类必须提供 VS Code IntelliSense 可识别的注释标签：

```cpp
/**
 * @brief 计算玩家与交互物之间的距离是否小于阈值。
 * @param [IN] playerPos 玩家脚底坐标（像素）。
 * @param [IN] targetPos 交互物脚底坐标（像素）。
 * @param [IN] radius 交互半径（像素）。
 * @return 在半径内返回 true，否则返回 false。
 */
bool IsWithinInteractRange(const Vec2& playerPos, const Vec2& targetPos, float radius);
```

6. 多返回值使用输出参数时标注 `@param [OUT]`；会修改的参数标注 `@param [IN/OUT]`。
7. 枚举使用 `enum class`，底层类型明确（如 `uint8_t`），并注明用途。
8. 所有 switch 覆盖 `default`；所有资源加载失败必须写日志并降级，不允许静默崩溃。
9. 禁止提交调试输出到最终 Release；调试日志通过 `Shared_Log` 统一控制。
10. 单文件超过约 800 行时，考虑按职责拆分，避免“上帝类”。

## 6. 构建规范

1. 根 `Makefile` 是唯一最终产物构建入口；`make` 默认生成 Release 与 Debug 两个 `Target.exe`。
2. 所有参与编译的目录必须显式加入 `CXX_INCLUDES_PATHS` 与 `CXX_SOURCES_PATHS`。
3. 新增源文件后必须验证 `make` 能索引到；不允许在业务代码中写相对 include 路径。
4. 最终产物必须静态链接（`-static`），不得依赖 MinGW 运行时 DLL。
5. 图形接口使用 D3D11；着色器在运行时由 `d3dcompiler_47.dll` 编译，该 DLL 属于 Windows 系统组件。
6. 资源通过 `windres` 以 RCDATA 嵌入，运行时从自身模块读取；禁止最终 exe 依赖外部资产路径。
7. 编译告警保持 `-Wall`；不得用强制关闭告警的方式掩盖问题。

---

## 7. 资源与编码规范

1. 所有文本文件使用 **UTF-8（无 BOM）**；换行符使用 **LF**。
2. 例外：Windows 专用 `.bat` 使用 **CRLF**。
3. `.gitattributes` 负责锁定文本类型与换行；新增文本扩展名时必须同步登记。
4. 二进制资产（`.png`、`.bmp`、`.bin`、`.ico`、`.docx`）标记为 `binary`，不做换行转换。
5. 美术资产统一由 `Resources/ArtGen` 生成，生成结果同时输出：
   - `Resources/Art/*.png`：供人审阅、可单独替换；
   - `Resources/ArtPack.bin`：游戏运行时读取的资产包。
6. 资产命名使用 ASCII 大写下划线，含义明确：`TILE_BAR_FLOOR_A`、`CHAR_PLAYER_WALK_S`、`UI_ICON_AMMO`。
7. 禁止把机器绝对路径、用户名、密钥、令牌写入任何入库文件；文档中的路径统一以 `.\` 为起点。
8. 下载或临时的外部素材只能放在 `Temp/`，确认授权与价值后再决定是否入库。

## 8. 美术与交互基调

1. 内部渲染分辨率 `480×270`，整数倍最近邻放大，保持像素边缘干净。
2. 16px 瓷砖、角色 16×24 或 24×32；对话头像 48×48。
3. 主色板：雨夜蓝黑、青绿霓虹、洋红警示、琥珀暖光、骨白文字。
4. 场景氛围优先级：酒吧内部“暖、拥挤、有人味”；酒吧外“湿冷、霓虹、孤独”；铁港仓库“工业、空旷、危险”。
5. UI 风格：终端化细线框、扫描线、轻微噪点；中文正文使用系统字体渲染，保证可读性。
6. 交互必须以“提示 + 反馈”成对出现：靠近显示 `[E]` 提示，执行后有音效/动画/文本反馈。
7. 重要操作不得只靠颜色区分；文本与图标同时表达状态。

## 9. 测试与验证规范

1. 默认只做针对性测试，不自动跑全量测试；只有用户明确要求“跑一遍所有测试”时才全量执行。
2. 所有自动化测试必须无头运行，不抢占鼠标、键盘、屏幕焦点。
3. `Tools/UnitTests`：纯逻辑单元测试（背包、任务、伤害、文本解析等），不得依赖 D3D/窗口。
4. `Tools/OffscreenTest`：创建隐藏窗口，初始化真实渲染管线，渲染指定场景并保存 BMP 截图到 `Temp/Screenshots/`。
5. 新增或修改工具后，必须更新 `Tools/README.md` 的用途、命令、产物路径与注意事项。
6. 每次阶段完成后，在 `Agent_Mem.md` 记录：执行命令、结果、已知问题。
7. 视觉验收以离屏截图为依据；禁止为了截图占用用户屏幕。

## 10. Git 规范

1. 本仓库使用本地 Git 管辖；提交身份仅在本工作区生效：

```text
user.name  = DeepSeek-V4.1-Flash
user.email = <>
```

2. 禁止修改全局 Git 配置。本工作区额外设置（仅本地）：

```text
core.autocrlf = false
core.eol = lf
```

3. 阶段性功能完善后才提交；一次提交对应一个可说明的阶段，不提交半成品或临时文件。
4. 初始文件已完成一次 init 提交；之后每次提交信息使用简洁中文，说明“改了什么 + 为什么”。
5. 多行提交信息写入 `Temp/` 下的 UTF-8 文件，通过 `git commit -F` 提交，避免终端截断。
6. 提交前检查：`git status` 无非预期文件；`Build/`、`Temp/`、`*.o`、`*.exe` 未入库。
7. 若发现提交包含敏感信息或隐私路径，立即在下一提交中移除并在记忆中登记。

## 11. 多 Agent 协作规范

1. 每位 Agent 接手工作时，第一步固定为：
   - 阅读 `Documents/Project_Rules.md`；
   - 阅读 `Documents/Agent_Mem.md` 的“当前状态 / 下一步 / 已知问题”；
   - 查看 `git log --oneline -5` 与 `git status`。
2. 完成任务后必须更新 `Agent_Mem.md`，包括：任务、改动文件、验证命令、结果、遗留问题、下一步建议。
3. `Agent_Mem.md` 必须保持可快速检索：固定章节、表格化阶段日志、明确的文件索引。
4. 不在记忆中写流水账；只记录对后续工作有价值的事实与决策。
5. 与其他 Agent 的接口变更（函数签名、资源名、场景 ID）必须写入“接口契约”章节。
6. 未经用户明确要求，不删除他人的阶段成果；如需替换，先记录原因。
